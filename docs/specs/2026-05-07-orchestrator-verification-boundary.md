# Orchestrator Verification Boundary and Named Cleanup Helpers

Source: TODO-5a12e2ea (verification-boundary half) + spec-design expansion for guardrail-friction cleanup-helper sites.

## Goal

This spec bundles two related tightenings of orchestrator behavior under a single principle: **orchestrators defer to named tools — subagents for substantive work, helper scripts for friction-prone mechanical work — and avoid ad hoc decisions in either dimension.**

**Verification-boundary half.** Tighten the boundary between orchestrators and their substantive-work subagents in three skills — `execute-plan`, `refine-code`, and `refine-plan` — so that orchestrators route subagent protocol output mechanically without re-judging the work themselves. The current procedures describe the happy path (dispatch, parse, forward) but do not explicitly forbid the orchestrator from inspecting implementation/review/plan content, running its own checks, overriding subagent verdicts, or inventing extra dispatches in the temptation gap between subagent return and protocol routing. This spec defines explicit prohibition language at those gaps so future orchestrator sessions cannot drift into duplicating the role of `verifier`, `test-runner`, `code-refiner`, or `plan-refiner` subagents.

**Cleanup-helpers half.** Replace two ad hoc orchestrator-emitted cleanup invocations — `rm -rf docs/test-runs/<plan-name>` and `find <dir> -type d -name __pycache__ -prune -exec rm -rf {} +` — with named helper scripts under `agent/skills/_shared/scripts/`. Both invocations are functionally safe (target known scratch / cache directories) but trip the project's recursive-delete guardrail, which currently halts the orchestrator's success path for a manual confirm. Named helpers shift the orchestrator-visible bash command to a non-matching helper path, eliminating the friction without weakening the guardrail.

## Context

### Verification-boundary half

The three affected skills follow the same pattern: an orchestrator dispatches one or more substantive-work subagents and processes structured protocol output. The substantive judgment — *does the implementation satisfy the criteria? does the review approve the change? does the plan cover the spec?* — lives entirely inside the dispatched subagent. The orchestrator's documented job is mechanical: assemble inputs, parse markers, validate provenance, route results.

Recent `execute-plan` session review (recorded in `docs/todos/5a12e2ea.md`) shows two observed classes of orchestrator-generated code. Allowed mechanical glue: filling prompt templates, extracting plan task blocks, resolving model tiers, assembling verifier-visible file sets, generating diff context, parsing protocol markers, and bookkeeping (moving plans, closing todos, checking provenance). Forbidden substantive verification: writing Python/grep/assertion scripts that independently check acceptance criteria, running spot checks against implemented files to decide whether criteria pass, creating final-acceptance scripts that re-check task-specific expected strings, directly running the integration test command instead of dispatching `test-runner`, writing `test-runner` artifacts from locally-run output, and interpreting local command output as evidence that a task passed.

The same temptation gap exists structurally in `refine-code` (between Step 5's `finalMessage` parse and Step 6's provenance validation, then before forwarding) and in `refine-plan` (between Step 9's `finalMessage` parse, Step 9.5's provenance validation, and Step 10's commit-gate routing). The orchestrator could in principle read the review file, re-inspect the diff, run additional commands, or override the coordinator's `STATUS:` line — none of which is documented as forbidden today. This spec extends the same boundary principle uniformly to all three skills as a single-source safeguard rather than three local rewordings.

Relevant code surface for the verification-boundary half:

- `agent/skills/execute-plan/SKILL.md` — Step 9 (worker status handling), Step 10 (wave gate), Step 11 (verification dispatch and parsing), Step 12 (post-wave commit and integration tests), Step 16 (final-gate integration regression).
- `agent/skills/refine-code/SKILL.md` — Step 5 (parse `code-refiner` `finalMessage`), Step 6 (validate review provenance and forward verbatim).
- `agent/skills/refine-plan/SKILL.md` — Step 9 (parse coordinator result), Step 9.5 (validate review provenance), Step 10 (status handling and commit gate).
- Existing static helper scripts under `agent/skills/execute-plan/scripts/` and `agent/skills/_shared/scripts/` (delivered via TODO-c6a7a5d0). These define the sanctioned mechanical surface that the new prohibition wording must explicitly preserve.

### Cleanup-helpers half

Two cleanup sites trip the recursive-delete guardrail's confirms during normal orchestrator success paths:

**Test-runs cleanup.** `agent/skills/execute-plan/SKILL.md` Step 16 currently bundles a `### 1. Move plan to done` substep that, after the final integration regression gate passes, runs `rm -rf docs/test-runs/<plan-name>`. This matches the guardrail's `\brm\s+(-[^\s]*r|--recursive)/i` dangerous-command regex and surfaces a manual confirm prompt every time a plan completes successfully.

**Pycache cleanup.** Pi sessions in pi-config (search of `~/.pi/agent/sessions/--Users-david-Code-pi-config--/` over recent runs) show orchestrators across `execute-plan`, `refine-code`, `refine-plan`, and code-review flows emitting `find agent -type d -name __pycache__ -prune -exec rm -rf {}` after running Python helpers under `agent/skills/.../scripts/` that leave bytecode caches behind. This command is **not** prescribed by any SKILL.md or agent definition (verified by repository grep — only the dangerous-command guardrail mentions `__pycache__`); it is emitted spontaneously as housekeeping. It matches the guardrail's `\bfind\b.*(?:\s-delete\b|\s-exec\s+rm\b)/i` regex and surfaces a separate manual confirm.

The per-plan `docs/test-runs/<plan-name>/` directory is flat by contract per `agent/skills/execute-plan/integration-regression-model.md` — only `baseline.log`, `wave-<N>-attempt-<K>.log`, and `final-gate-<seq>.log` files (`agent/skills/execute-plan/SKILL.md:287–292`). The directory under cleanup for the pycache helper is the orchestrator's working subtree (typically `agent` in pi-config, but generalizable).

Both cleanups are functionally safe but indistinguishable from genuinely dangerous recursive deletes at the regex level. The guardrail's stated philosophy explicitly accepts that "this is not a full security system… it is meant to catch high-signal mistakes and add friction around risky actions" — so some misplaced friction is by design. Two structural responses are available:

1. **Loosen the guardrail** with a path-based allow-list for known-safe targets. Requires guardrail parsing changes (the existing `extractSimpleBashWriteTargets` does not cover `rm` or `find` argument extraction), weakens the "every recursive delete confirmed" invariant, and does not generalize to future cleanup sites without further allow-list additions.
2. **Replace the dangerous-looking command with a named helper invocation.** The orchestrator-visible bash command becomes the helper path (e.g. `python3 agent/skills/_shared/scripts/cleanup-test-runs.py docs/test-runs/foo`), which does not match either dangerous-command regex. The helper's argument validation makes its internal `rm -rf` / `find -exec rm` safe by ruling out path-confusion mistakes.

This spec adopts (2). The guardrail stays as-is; the cleanup mechanism becomes explicit and auditable; the friction disappears for the two known sites.

The existing convention for shared mechanical scripts is established at `agent/skills/_shared/scripts/`, which currently contains six `.py` helpers (`resolve-model-dispatch.py`, `validate-review-provenance.py`, `parse-artifact-handoff.py`, `fill-template.py`, `classify-workflow-drift.py`, `extract-provenance-preamble.py`) with tests under `agent/skills/_shared/scripts/tests/`. New helpers in this spec follow that convention.

## Requirements

### Verification-boundary requirements

1. **Execute-plan: explicit prohibition after coder return.** The skill must contain prominent guardrail language at the Step 9 / Step 10 / Step 11 boundary stating that after a `coder` returns `DONE` or `DONE_WITH_CONCERNS`, the orchestrator MUST NOT run local grep / Python / assertion scripts, spot checks, or final-acceptance checks to decide whether the implementation satisfies the task. The only sanctioned path for substantive task verification is dispatching a fresh `verifier` subagent with the planner-authored acceptance criteria and `Verify:` recipes, then mechanically parsing the verifier's protocol output.
2. **Execute-plan: explicit prohibition for integration tests.** The skill must contain language at the Step 7 / Step 12 / Step 16 integration-test sites stating that the orchestrator MUST NOT run the configured test command itself or synthesize a `test-runner` artifact from locally-run output. All integration-test execution and artifact writing must be performed by the `test-runner` subagent; the orchestrator may only create the parent directory, dispatch `test-runner`, parse the artifact handoff marker, validate the artifact format, and reconcile parsed results against the frozen `baseline_failures` per `integration-regression-model.md`.
3. **Execute-plan: enumerate allowed mechanical work.** The skill must list the allowed mechanical-glue activities (prompt template assembly, plan parsing, model-tier resolution, verifier-visible file-set assembly, diff context generation, protocol-marker parsing, completion bookkeeping) and pair each with the relevant existing helper script where one exists. The list must clarify that allowed mechanical work never produces a substantive PASS/FAIL verdict on implementation acceptance criteria.
4. **Refine-code: explicit prohibition between parse and forward.** The skill must contain guardrail language at Step 5 / Step 6 stating that the orchestrator MUST NOT (a) read the review file or the diff to form an independent verdict, (b) override the `STATUS:` line returned by the `code-refiner`, (c) run local checks (grep, test commands, additional `Read` calls on implementation files) to second-guess the coordinator's judgment, or (d) dispatch ad hoc remediation subagents outside the documented loop. The only sanctioned post-coordinator path is parsing `finalMessage` for the `STATUS:` line, validating provenance via the shared script, and forwarding the coordinator's output verbatim.
5. **Refine-plan: explicit prohibition between parse and commit.** The skill must contain guardrail language at Step 9 / Step 9.5 / Step 10 stating that the orchestrator MUST NOT (a) read the review files or plan content to form an independent verdict, (b) override the `STATUS:` line returned by the `plan-refiner`, (c) run local checks against the plan to second-guess the coordinator's judgment, or (d) edit the plan or invent extra refinement dispatches outside the documented loop. The only sanctioned post-coordinator paths are parsing `finalMessage`, validating each review file's provenance, and routing on `STATUS:` to the commit gate.
6. **Shared boundary principle stated once.** The three skills must reference a shared, single-source-of-truth statement of the orchestrator-verification boundary so the principle remains consistent if it is later revised. The shared statement must articulate that orchestrators route substantive subagents mechanically and never re-judge their output.
7. **Skill-specific forbidden-behavior examples.** Each skill's hot-spot guardrail must include a short forbidden-behavior list (illustrative, not exhaustive) tailored to that skill's surface — for `execute-plan`, mirroring the recommended wording in TODO-5a12e2ea; for `refine-code` and `refine-plan`, covering review-file inspection, `STATUS:` override, ad hoc local checks, and out-of-loop dispatches.

The cleanup target, timing, and conditions stay identical — only the grouping changes. If the archive flow is retained instead, the existing cleanup placement is preserved.

### Cleanup-helper requirements

11. **Test-runs cleanup helper.** A new script at `agent/skills/_shared/scripts/cleanup-test-runs.py` MUST exist that takes a per-plan directory path as a positional argument, validates it (Requirement 13), and removes the directory recursively via `shutil.rmtree`. The orchestrator-visible bash invocation MUST be of the form `python3 agent/skills/_shared/scripts/cleanup-test-runs.py <path>` so the guardrail's `\brm\s+(-[^\s]*r|--recursive)/i` regex does not match.
12. **Pycache cleanup helper.** A new script at `agent/skills/_shared/scripts/cleanup-pycache.py` MUST exist that takes a directory path as a positional argument, validates it (Requirement 13), and removes all `__pycache__` directories under it (equivalent to `find <dir> -type d -name __pycache__ -prune -exec rm -rf {} +`, implemented in Python via `os.walk` + `shutil.rmtree` or equivalent). The orchestrator-visible bash invocation MUST be of the form `python3 agent/skills/_shared/scripts/cleanup-pycache.py <path>` so the guardrail's `\bfind\b.*(?:\s-delete\b|\s-exec\s+rm\b)/i` regex does not match.
13. **Helper argument validation.** Both helpers MUST refuse arguments where any of the following hold, exiting non-zero with a clear error message:
    - The argument contains a `..` traversal segment.
    - After resolution via `os.path.realpath`, the argument is outside the current working directory tree.
    - After resolution, the path's segments include any of the hard-protected segments enumerated in the guardrail's protected-segment list (`.git`, `.ssh`, `node_modules`, `.venv`, `venv`).
    Additionally, the test-runs helper MUST require that the resolved path is under `<cwd>/docs/test-runs/`. The pycache helper places no further path constraint beyond the protected-segment check (the cache target is project-local but its parent can be any working subtree).
14. **Helper documentation in skills.** `agent/skills/execute-plan/SKILL.md` MUST reference `cleanup-test-runs.py` as the sanctioned cleanup invocation at the test-runs cleanup site (whether retained inside the archive flow or relocated per Requirement 10). `agent/skills/execute-plan/SKILL.md`, `agent/skills/refine-code/SKILL.md`, and `agent/skills/refine-plan/SKILL.md` MUST each contain a single short reference to `cleanup-pycache.py` as the sanctioned mechanism for cleaning Python bytecode caches left behind by their helper-script invocations, so the orchestrator does not re-derive the `find ... -exec rm` form ad hoc. Co-locating the reference with the existing allowed-mechanical-work block (Requirement 3 for execute-plan, equivalent locations in refine-code/refine-plan) is acceptable.
15. **Helper tests.** Both helpers MUST have tests under `agent/skills/_shared/scripts/tests/` covering: (a) successful cleanup of a present target path; (b) idempotent / no-op behavior when the target is already absent or empty; (c) refusal of `..`-traversal arguments; (d) refusal of arguments resolving outside cwd; (e) refusal of arguments matching any hard-protected segment from Requirement 13; (f) for the test-runs helper specifically, refusal of arguments not under `<cwd>/docs/test-runs/`. Test style follows the existing convention under `agent/skills/_shared/scripts/tests/` (e.g. the `conftest_path_stubs.py` pattern from `agent/skills/define-spec/scripts/tests/`).

## Constraints

- Existing skill behavior MUST be preserved except for: (a) the addition of guardrail language and the cross-references that anchor it, (b) the optional removal of the plan-archive-to-done flow per Requirement 9 with cascading cleanup of its references, (c) the relocation of test-runs cleanup per Requirement 10 (if (b) is exercised), and (d) the substitution of helper invocations for inline `rm -rf` / `find -exec rm` per Requirements 11–14. No procedural changes to wave dispatching, retry budgets, commit gates, integration-test reconciliation, provenance validation, or any other documented step beyond what these four points require.
- The static helper scripts already delivered under `agent/skills/execute-plan/scripts/` and `agent/skills/_shared/scripts/` (per TODO-c6a7a5d0) MUST remain the sanctioned mechanical surface. The new wording MUST NOT prohibit existing helpers or change their CLIs. The two new helpers (`cleanup-test-runs.py`, `cleanup-pycache.py`) extend the surface but follow the same convention (location, language, invocation style).
- The new wording MUST NOT change the public command shape, prompt templates, dispatch shape, or `(model, cli)` resolution rules of the three skills.
- The shared boundary statement MUST live in a single source-of-truth file so the three skill `SKILL.md` files reference it instead of restating it. The exact location is a planner choice; this spec only requires that the statement is not duplicated.
- The new wording MUST NOT introduce ambiguity around already-permitted mechanical activities. Dispatching `verifier` / `test-runner` / `code-refiner` / `plan-refiner`, parsing protocol output, running provenance validation scripts, computing diff context, bookkeeping (closing todos, checking git status), and invoking the new cleanup helpers all remain explicitly allowed.
- The boundary is held by SKILL.md language, not by runtime enforcement or linting. No script-level gates are added beyond the helpers' own argument validation.
- The dangerous-command guardrail implementation MUST NOT be modified by this work. The cleanup-helper strategy is deliberately chosen to keep the guardrail unchanged; loosening the guardrail with path-based allow-lists is explicitly out of scope.
- Both cleanup helpers' internal implementations MAY use `shutil.rmtree`, `os.walk`, or equivalent. The guardrail interception happens at the bash-tool boundary (the `python3 ...` invocation), not inside the helper process — so internal recursive deletion is safe provided argument validation has run first. Helpers MUST validate before deleting.

## Approach

**Verification-boundary half — chosen approach:** Documentation-only safeguards. Add explicit prohibition language at the existing temptation hot spots in each skill, anchored on a single shared boundary statement that all three skills reference. Keep the orchestration shape — parallel coder waves, separate verifier waves, single-coordinator `refine-code` / `refine-plan` dispatches — exactly as it is today.

*Why this over alternatives:* TODO-5a12e2ea's acceptance criteria are met by wording alone, and the TODO explicitly frames the coder→verifier-pairing exploration as "without assuming it is definitely the right implementation." Documentation-only also generalizes uniformly to `refine-code` and `refine-plan`, which have no parallel surface to pair.

*Considered and rejected:*

- **Pair-style architecture for `execute-plan`** (each task as a `subagent_run_serial { coder, verifier }` pair, parallel across the wave). Closes the gap structurally but breaks four existing wave-model invariants: (1) the Step 10 wave gate runs *before* Step 11 today, so users see BLOCKED siblings before verification fires; (2) NEEDS_CONTEXT mid-wave re-dispatch cannot easily be wrapped in a serial pair; (3) wave-level `git diff HEAD` context for verifiers would surface other in-flight wave tasks' working-tree changes; (4) Step 10's sub-task split path dispatches sub-tasks pre-commit and relies on a wave-level diff still being intact at Step 11. Pair-style also does not help `refine-code` / `refine-plan`, so adopting it would only address one of the three skills.
- **Pair-style + documentation-only layered together.** Inherits every downside of pair-style on top of the wording change, with no marginal safety benefit while wording is present.

**Cleanup-helpers half — chosen approach:** Two named, validated Python helper scripts under `agent/skills/_shared/scripts/` (matching the existing six-helper convention there), each replacing a friction-prone ad hoc invocation. The orchestrator-visible bash command becomes a `python3 agent/skills/_shared/scripts/cleanup-*.py <arg>` call, which the dangerous-command regexes do not match. Argument validation inside each helper enforces a narrow safe surface (no `..`, must resolve under cwd, no protected segments, plus path-prefix constraint for the test-runs helper) so that internal use of `shutil.rmtree` / equivalent is safe even though the regex no longer fires.

*Why this over alternatives:*

- **Loosen the guardrail with a path-based allow-list.** Requires non-trivial parsing additions to the dangerous-command guardrail (the existing `extractSimpleBashWriteTargets` covers redirection / tee / cp / mv / dd, not `rm` or `find`), introduces a new "skip confirm if path matches X" code path that weakens the guardrail's "every recursive delete confirmed" invariant, and forces every future safe-cleanup site to be added to the allow-list as a guardrail edit. Helpers generalize trivially — one helper per friction site, opt-in adoption — and keep the guardrail itself unchanged.
- **Move-to-tmp instead of delete.** Functionally bypasses the guardrail but doesn't actually free space and relies on OS tmp-cleanup behavior that varies. Not a real cleanup.
- **Flat-delete + `rmdir` for test-runs only.** Earlier conversation surfaced this as a no-helper option for the test-runs site (the directory is flat by contract). Workable for that one site but doesn't help the pycache site (deeply nested by nature) and offers no validation surface, so it's strictly worse than the helper approach when both sites are in scope.

## Non-Goals

- This spec does NOT change wave dispatching shape, retry budgets, commit gates, integration-test reconciliation, provenance validation, or any existing helper script behavior.
- This spec does NOT introduce new helper scripts beyond the two cleanup helpers, modify existing helper script CLIs, or extract additional skills (those are TODO-c6a7a5d0 / TODO-b733a4af territory).
- This spec does NOT decide the coder→verifier pair-style architecture question; it is recorded as an open follow-up.
- This spec does NOT add automated linting or runtime checks that detect orchestrator overreach. Boundary discipline is held by SKILL.md language only.
- This spec does NOT modify other skills (e.g. `generate-plan`, `define-spec`, `commit`) even if structurally similar verification gaps exist there. Scope is limited to the three skills explicitly named for the verification-boundary half. The cleanup-pycache helper reference appears in `execute-plan` / `refine-code` / `refine-plan` only because those are the orchestrators known to run the Python helpers that produce the caches; if other skills are later observed to have the same friction, they can be amended to reference the helper without re-spec.
- This spec does NOT alter agent definitions under `agent/agents/` (e.g. `coder.md`, `verifier.md`, `test-runner.md`, `code-refiner.md`, `plan-refiner.md`). Those define what the subagents do; this spec constrains only the orchestrator's behavior around them.
- This spec does NOT modify the dangerous-command guardrail implementation, add path-based allow-lists, or otherwise alter the guardrail's recursive-delete confirm logic. The cleanup-helper approach is the entire response to the guardrail-friction motivation.
- This spec does NOT define a generic cleanup-helper framework or shared utility module. The two helpers are independent scripts with their own validation; cross-helper abstraction is out of scope and would be premature for two helpers.
- This spec does NOT specify the implementation language of the helpers beyond following the existing `agent/skills/_shared/scripts/` Python convention. If a future planner has reason to break that convention, that is a separate decision.

A future todo can revisit if documentation-only safeguards prove insufficient in practice.
- **Shared boundary file location.** The spec requires a single source-of-truth file but does not pick its path; final placement is a planner choice. Candidates worth considering include co-locating with `agent/skills/_shared/coordinator-dispatch.md` (the existing shared dispatch authority) or a new `agent/skills/_shared/orchestrator-verification-boundary.md`.
- **Direct-evidence search for `refine-code` / `refine-plan` overreach.** A pi-config session search did not surface a smoking-gun incident of orchestrator overreach inside `refine-code` / `refine-plan` runs (as distinct from pi-config development sessions touching review files).
