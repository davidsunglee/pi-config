## Context

`execute-plan` has grown into a large orchestration monolith. Several parts are reusable outside plan execution and should be extracted into standalone skills or shared protocols, leaving `execute-plan` as the high-level coordinator.

Current rough estimate: extracting the first four recommendations could save ~175–225 lines from `agent/skills/execute-plan/SKILL.md` (from ~771 lines down to roughly ~550–600), while moving detailed protocols into focused skills.

## Recommended extractions

### 1. `run-test-artifact` / `test-runner-dispatch`

Extract the parent/orchestrator-side protocol for running integration tests through the `test-runner` subagent.

Responsibilities:
- Given `{test_command, working_dir, artifact_path, phase_label}`, fill the test-runner prompt.
- Resolve `test-runner` model/CLI via `crossProvider.cheap` and `_shared/model-tier-resolution.md`.
- Dispatch `test-runner` via `subagent_run_serial`.
- Validate `TEST_RESULT_ARTIFACT` marker.
- Check marker path equals expected artifact path.
- Verify artifact exists and is non-empty.
- Parse/validate structured artifact header.
- Return `exit_code`, `failing_identifiers`, `non_reconcilable_failures`, and artifact path.

Why:
- Cleanest extraction boundary.
- Useful outside `execute-plan` anywhere we want subagent-run tests with durable artifacts.

Estimated execute-plan savings: ~25–35 lines.

### 2. `verify-implementation` / `acceptance-verification`

Extract the verification gate for completed work. Avoid naming it `verify-plan-task` because the thing being verified is not the plan; it is the implemented work.

Core principle:

> Verify completed implementation against the best available acceptance contract. If no explicit contract exists, derive a provisional one from the request and clearly label the result as inferred verification.

Two operating modes:

#### Strict mode: explicit acceptance contract exists

Used by `execute-plan`.

Inputs may include:
- Task spec from a plan.
- Acceptance criteria.
- `Verify:` recipes.
- Worker report / changed files.
- Working directory.
- Orchestrator-observed diff/files.

Responsibilities:
- Require every acceptance criterion to have a `Verify:` recipe when running in strict execute-plan mode.
- Assemble verifier-visible files from task-declared scope, worker-reported changes, and observed git diff/status.
- Build uncommitted diff context, including no-index diffs for new files and truncation markers for large diffs.
- Fill `verify-task-prompt.md` or a generalized equivalent.
- Resolve `verifier` model/CLI via `crossProvider.standard`.
- Dispatch verifier subagents.
- Parse `## Per-Criterion Verdicts` and `VERDICT: PASS|FAIL`.
- Treat malformed verifier output/protocol errors as verification failures.
- Return per-criterion verdicts and an overall PASS/FAIL.

#### Ad hoc mode: no formal plan exists

Used for one-off tasks, e.g. a user asks for a small change from a one-line description.

Inputs may be as little as:
- Original user request / one-line task description.
- Current git diff / changed files.
- Optional test command.
- Optional conversation context.

Responsibilities:
- Reconstruct implied acceptance criteria from the request.
- Inspect changed files and diff.
- Run relevant tests if discoverable or supplied.
- Check obvious behavior implied by the task.
- Return one of:
  - `PASS` — explicit or confidently inferred criteria are satisfied.
  - `FAIL` — implementation clearly does not meet the request.
  - `INSUFFICIENT_SPEC` — the request is too vague to verify strongly.
- Clearly label inferred criteria and confidence limits.

Why:
- This is reusable beyond plan execution.
- It supports both formal plan tasks and lightweight one-off implementation checks.
- It reduces Step 11 substantially while improving verification as a general capability.

Estimated execute-plan savings: ~45–55 lines.

### 3. `integration-regression-gate`

Extract the frozen-baseline reconciliation model and gate behavior.

Responsibilities:
- Capture baseline using `run-test-artifact`.
- Freeze `baseline_failures` for the whole run.
- Handle baseline with stable failures only.
- Handle baseline with non-reconcilable failures via explicit user decision.
- For each later run, compute:
  - `current_failing_stable`
  - `current_non_reconcilable`
  - `current_non_baseline_stable = current_failing_stable \ baseline_failures`
- Render the canonical three-section user-facing summary.
- Provide post-wave menus:
  - intermediate wave: debug / continue / stop
  - final wave: debug / stop
- Provide final completion gate: debug / stop only.

Why:
- The baseline-only reconciliation rules are complex and reusable.
- Step 7, Step 12, and Step 16 all consume the same model.
- Existing `integration-regression-model.md` is already a strong seed for this extraction.

Estimated execute-plan savings: ~75–95 lines.

### 4. `debug-integration-regression`

Extract the Debugger-first flow currently shared by Step 12 and Step 16.

Responsibilities:
- Given current integration failures and a changed-file universe, identify suspect tasks/files.
- Dispatch a single debugging pass using `coder` with explicit instruction to follow `systematic-debugging`.
- Require root-cause investigation before fixes.
- Allow localized fix in same dispatch with TDD evidence.
- If diagnosis-only, dispatch targeted remediation for implicated files/tasks.
- Commit remediation using caller-provided template.
- Re-run the relevant integration gate via `run-test-artifact` / `integration-regression-gate`.
- Avoid blanket re-dispatch of unrelated tasks.
- Respect caller-specific undo behavior:
  - post-wave may offer wave-commit undo after targeted remediation fails;
  - final-gate must not undo prior wave commits.

Why:
- It is already parameterized between post-wave and final-gate contexts.
- It is reusable for any integration regression discovered after a change range.

Estimated execute-plan savings: ~30–40 lines.

### 5. `subagent-wave-gate` / `coder-wave-coordination`

Potential later extraction. More coupled than the first four.

Responsibilities:
- Handle worker status codes: `DONE`, `DONE_WITH_CONCERNS`, `NEEDS_CONTEXT`, `BLOCKED`.
- Drain full wave before intervention.
- Present combined blockers and concerns.
- Offer canonical blocker interventions: more context, better model, split into subtasks, stop.
- Handle concerns remediation.
- Maintain shared retry budget across blocked handling, concerns remediation, and verification failures.

Why:
- Large chunk of execute-plan.
- Reusable for other multi-agent implementation workflows.

Caution:
- More intertwined with execute-plan task/wave state, model tiers, and retry semantics. Extract after smaller seams are proven.

### 6. `execution-workspace-preflight`

Optional extraction.

Responsibilities:
- Detect git repo.
- Detect linked worktree vs main checkout.
- Detect feature branch vs main/master/develop.
- Dirty workspace safety prompt.
- Decide reuse current workspace vs create new worktree.
- Invoke `using-git-worktrees` when needed.

Why:
- Reusable for other long-running implementation workflows.

Caution:
- Lower line savings and less central to the monolith problem than test/verification/gate flows.

## Suggested extraction order

1. `run-test-artifact` — lowest-risk, clearest boundary.
2. `verify-implementation` / `acceptance-verification` — strong standalone skill; make it plan-agnostic with strict and ad hoc modes.
3. `integration-regression-gate` — depends on test artifact runner.
4. `debug-integration-regression` — depends on integration gate.
5. `subagent-wave-gate` — valuable but more coupled; do after the smaller extractions.
6. `execution-workspace-preflight` — optional cleanup.

## Non-goals / keep in execute-plan for now

- Plan location and structural validation.
- Dependency graph parsing and wave grouping.
- Model-tier resolution docs already live in `_shared/model-tier-resolution.md`; do not duplicate unless there is a specific need.
- Final plan movement to `docs/plans/done/`, linked todo closure, and branch completion can stay in execute-plan for now because they are thin and plan-specific.
