## Context

`execute-plan` rejected `docs/plans/2026-05-11-2026-05-11-fast-lane-workflow.md` with:

```json
{"kind": "missing_required_section", "section": "numbered_tasks"}
```

Root cause: the plan used H3 task headings like:

```md
### Task 1 — Add the `recommend-workflow.py` helper (TDD)
```

but `agent/skills/execute-plan/scripts/extract-plan-tasks.py` only recognizes:

```py
^### Task (\d+):\s*(.*)
```

After normalizing headings in memory from `### Task N —` to `### Task N:`, the parser accepted the plan: 7 tasks, 0 errors, waves `[1,3]`, `[2,4]`, `[5,6]`, `[7]`.

## Recommendation

Prefer narrowly relaxing parsers at human-/LLM-authored Markdown boundaries over relying on planner/reviewer agents to police minor punctuation/capitalization drift. Keep machine-protocol/artifact parsers strict.

## Primary target: `extract-plan-tasks.py`

This parser consumes human/LLM-authored plans, so it should be tolerant of unambiguous Markdown variants while preserving executor safety.

### Suggested implementation

1. Relax the task heading regex narrowly while keeping the canonical generated format as colon:

```py
^### Task (\d+)\s*(?::|—|–|-)\s*(.*)
```

This keeps the contract strict enough:
- H3 only
- literal `Task N`
- ordered numeric tasks still enforced
- requires a separator
- accepts common Markdown title punctuation

2. Keep planner docs/guidance canonical as:

```md
### Task N: Title
```

3. Improve diagnostics: if the parser sees lines matching `^### Task \d+\b` but not the accepted heading shape, emit a targeted protocol error such as:

```json
{"kind": "malformed_task_heading", "line": 52, "heading": "### Task 1 ..."}
```

rather than the misleading `missing_required_section: numbered_tasks`.

4. Consider safe label/section leniency inside `extract-plan-tasks.py`:
   - Accept task section labels case-insensitively where semantics are unambiguous:
     - `**Files:**`
     - `**Steps:**`
     - `**Acceptance criteria:**` / `**Acceptance Criteria:**`
     - `**Model recommendation:**` / `**Model Recommendation:**`
   - Accept file-scope prefixes case-insensitively as today (`Create:`, `Modify:`, `Test:` already effectively do this).
   - Accept `Verify:` case-insensitively (`Verify:`, `verify:`) for acceptance criteria recipes, while still requiring exactly one immediately-following recipe line per criterion.
   - Consider accepting common top-level heading capitalization variants for required sections, especially:
     - `## Architecture Summary` in addition to `## Architecture summary`
     - `## Tech Stack` in addition to `## Tech stack`
     - existing `## Risk Assessment` / `## Risk assessment`
   - Keep required section names semantically specific; do not accept vague aliases like `## Implementation` for `## Tasks`.

5. Add unit fixtures/tests in `agent/skills/execute-plan/scripts/tests/` for:
   - colon heading accepted: `### Task 1: Title`
   - em dash heading accepted: `### Task 1 — Title`
   - en dash / hyphen accepted if implemented
   - malformed task-like heading produces `malformed_task_heading` instead of `missing_required_section`
   - `**Acceptance Criteria:**` and `**Model Recommendation:**` capitalization variants parse successfully if implemented
   - lowercase `verify:` parses successfully if implemented
   - existing fence-aware tests still pass; headings/labels inside fenced code blocks must not be parsed as structure

## Secondary target: `extract-provenance-preamble.py`

This parser also consumes human-authored Markdown preambles. It currently accepts only plain lines such as:

```md
Source: TODO-12345678
Scout brief: docs/briefs/example.md
Git SHA: <40 lowercase hex chars>
```

Recommendation: add small, explicit leniency for bold Markdown label variants that this repo commonly uses elsewhere:

```md
**Source:** TODO-12345678
**Scout brief:** docs/briefs/example.md
**Git SHA:** <40 lowercase hex chars>
```

Potential implementation:
- Accept both plain and bold forms for `Source`, `Scout brief`, and `Git SHA`.
- Preserve existing bounded preamble and fence-aware behavior.
- Preserve strict TODO shape (`TODO-<8 lowercase/hex chars>`, currently case-sensitive via `[0-9a-f]` unless intentionally changed).
- Preserve strict scout-brief path shape (`docs/briefs/<file>`) unless there is evidence broader paths are needed.
- Preserve strict SHA validation for brief mode; malformed SHA should still produce `git_sha_malformed`.

Add tests for bold Source/Scout/Git SHA lines and confirm fake provenance inside fences remains ignored.

## Parsers that should stay strict

Do **not** proactively relax machine-protocol/artifact parsers unless there is a concrete failure with a safe compatibility story:

- `agent/skills/_shared/scripts/parse-artifact-handoff.py` — strict terminal marker protects artifact handoff integrity.
- `agent/skills/_shared/scripts/parse-test-runner-artifact.py` — strict headers/counts protect test-run reconciliation correctness.
- `agent/skills/execute-plan/scripts/parse-verifier-report.py` — strict criterion/verdict/evidence format prevents bad verification reports from passing.
- `agent/skills/_shared/scripts/validate-review-provenance.py` — strict provenance gates reviewer model/CLI trust.
- `agent/skills/execute-plan/scripts/parse-coder-report.py` — keep status tokens strict; section parsing already tolerates missing sections by returning empty blocks where appropriate.
- `agent/skills/refine-code/scripts/parse-refine-code-summary.py` — already has targeted leniency for `## Remaining Issues (...)`; keep the rest protocol-oriented.
- `agent/skills/refine-plan/scripts/parse-refine-plan-summary.py` and `validate-and-parse-plan-review.py` — keep strict unless a concrete model-output failure justifies a narrow compatibility case.

## Rationale

This is a parser-boundary issue. The plan was substantively structured and otherwise parser-valid; execution failed due to punctuation. Mechanical parser tolerance is more robust than asking every generation/review loop to catch the exact separator manually. If generation-time safety is desired later, run the same parser mechanically after generation/refinement rather than relying on model judgment.

## Additional observation: `parse-coder-report.py` rejected Markdown-heading status

During execution of `docs/plans/2026-05-11-2026-05-11-fast-lane-workflow.md`, Task 1 completed substantively but its first report began with:

```md
## STATUS: DONE
```

`agent/skills/execute-plan/scripts/parse-coder-report.py` requires an unfenced line matching `^STATUS:\s*(\S+)`, so it emitted `status_line_missing` and the orchestrator retried solely to obtain a protocol-valid report. The retry did not change the implementation.

This may be unnecessarily strict for a coder report authored by an LLM in Markdown. Consider a narrow compatibility relaxation while keeping the protocol safety properties:

```py
^(?:#{1,6}\s+)?STATUS:\s*(DONE|DONE_WITH_CONCERNS|BLOCKED|NEEDS_CONTEXT)\s*$
```

Safety constraints to preserve:
- Remain fence-aware; status lines inside fenced code blocks must not count.
- Keep the status token set strict.
- Prefer the first real status line outside fences, as today.
- Do not accept prose variants like `Status is done` or unknown status tokens.
- Add regression tests for both canonical `STATUS: DONE` and Markdown-heading `## STATUS: DONE`, plus a fenced fake heading that must be ignored.

### Complementary prompt hardening

Also tighten worker prompts so protocol-valid output is more likely before parser fallback is needed. For example, in `agent/skills/execute-plan/execute-task-prompt.md` and any derived coder prompts, change the Report Format instruction from:

```md
Use this exact structure:
```

to something like:

```md
Your first non-fenced line MUST be exactly `STATUS: <DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT>` with no Markdown heading marker, bullet, bolding, or preamble. Do not write a summary before the STATUS line.
```

This reduces unnecessary retries while the parser relaxation handles harmless existing-model Markdown formatting drift.

## Additional observation: `refine-code` failed on missing `REVIEW_ARTIFACT` marker despite expected review file

During execution of `docs/plans/2026-05-11-2026-05-11-fast-lane-workflow.md`, final review stopped with:

```md
STATUS: failed

## Failure Reason
reviewer artifact handoff failed: missing REVIEW_ARTIFACT marker
```

The `code-refiner` reported that a review file existed at:

```text
/Users/david/Code/pi-config/docs/reviews/2026-05-11-2026-05-11-fast-lane-workflow-code-review-v1.md
```

and it had already completed one remediation commit:

```text
c0dab04 fix(review): iteration 1 — baseline comparison contract
```

This is a concrete artifact-handoff failure with a safe compatibility story. The `REVIEW_ARTIFACT:` marker is a transport handoff; the on-disk review file plus provenance/verdict validation is the source of truth.

### Recommendation: tighten prompt + add expected-path fallback

Do both, but prioritize the deterministic fallback.

1. **Prompt hardening** in `agent/agents/code-reviewer.md` and `agent/skills/requesting-code-review/review-code-prompt.md`:

   Replace permissive language like "Conversational text before the marker line is permitted" with a stricter terminal-message contract for refiner-driven reviews:

   ```md
   After writing the review file, your final assistant message MUST be exactly one line:
   REVIEW_ARTIFACT: <absolute path>

   No summary. No prose. No markdown. No additional lines. This must be the final assistant message.
   ```

   Keep the existing `subagent_done(message="REVIEW_ARTIFACT: <absolute path>")` instruction. Prompt tightening reduces future misses but should not be the only protection.

2. **Narrow expected-path fallback** in the `refine-code` / `code-refiner` handoff path:

   If `parse-artifact-handoff.py --marker REVIEW_ARTIFACT ...` fails only with `handoff_missing` / missing marker, the coordinator may still accept the known expected artifact path **only when all deterministic checks pass**:

   - expected review file exists and is non-empty;
   - expected path is the exact path the coordinator supplied to the reviewer for this dispatch (no path inferred from model prose);
   - first non-empty line is byte-equal to the supplied `**Reviewer:** <provider>/<model> via <cli>` provenance line for this dispatch;
   - `validate-review-provenance.py --review-file <path> --allowed-tiers <tier>` passes;
   - `**Verdict:**` line is present and parses as one of `Approved`, `Approved with concerns`, or `Not approved`;
   - artifact freshness is established, e.g. mtime is after dispatch start or file hash/mtime changed from the pre-dispatch snapshot.

   If these checks pass, treat the missing marker as a handoff warning and continue using the on-disk file as authoritative. If any check fails, preserve the current hard failure.

### Do not broadly relax artifact validation

Keep hard failures for:

- missing/empty expected review file;
- path mismatch when a marker is present but points elsewhere;
- malformed or stale provenance;
- missing/unrecognized verdict;
- stale artifact that was not freshly written by the reviewer dispatch;
- marker-like text inside quoted/code blocks or anywhere other than the accepted terminal marker path.

### Possible helper/API shape

Prefer implementing this as an explicit option/helper mode rather than weakening `parse-artifact-handoff.py` globally. For example:

```bash
parse-artifact-handoff.py \
  --marker REVIEW_ARTIFACT \
  --final-message <path> \
  --expected-path <expected-review-path> \
  --check-existence \
  --check-non-empty \
  --allow-missing-marker-if-expected-artifact-valid \
  --fresh-after <dispatch-start-timestamp>
```

or keep `parse-artifact-handoff.py` strict and add a refine-code-specific wrapper/helper such as `validate-review-artifact-handoff.py` that first tries strict marker validation, then applies the expected-path fallback only for missing-marker failures.

### Regression tests to add

- Marker present, expected path, valid provenance/verdict → pass (existing strict path).
- Marker missing, expected file exists, fresh, valid provenance/verdict → pass with a warning/fallback flag.
- Marker missing, expected file missing/empty → fail.
- Marker missing, expected file stale (mtime/hash unchanged from before dispatch) → fail.
- Marker missing, provenance line differs from supplied reviewer provenance → fail.
- Marker missing, verdict missing/unrecognized → fail.
- Marker present but path mismatches expected path → fail (do not fallback silently).
- Marker-looking line inside fenced/quoted text still does not count as the strict handoff marker.
