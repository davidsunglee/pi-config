## Summary

Several planning/execution failures came from boundary mismatches rather than substantive plan or code issues:

- human-/LLM-authored Markdown used harmless punctuation/capitalization variants that strict parsers rejected;
- LLM-authored protocol reports used Markdown heading syntax around otherwise valid status lines;
- `refine-code` failed when the expected on-disk review artifact existed but the terminal `REVIEW_ARTIFACT:` transport marker was missing;
- `generate-plan` needs safer user choices when refinement exhausts its iteration budget without approval.

The unifying goal is **targeted tolerance at human/LLM-authored boundaries, strict validation for machine-trust decisions, and clearer failure/continuation UX**.

## Guiding principles

- Relax only narrow, unambiguous Markdown variants at human-/LLM-authored input boundaries.
- Keep canonical prompts/docs strict so new artifacts continue to use the preferred format.
- Preserve fence-aware parsing: structure inside fenced code blocks must not count.
- Keep machine-trust gates strict unless there is a deterministic fallback with equivalent validation.
- Prefer targeted diagnostics over misleading generic errors.

## 1. `execute-plan`: tolerate safe human-authored plan Markdown variants

### Observed failure

`execute-plan` rejected `docs/plans/2026-05-11-2026-05-11-fast-lane-workflow.md` with:

```json
{"kind": "missing_required_section", "section": "numbered_tasks"}
```

Root cause: the plan used H3 task headings like:

```md
### Task 1 — Add the `recommend-workflow.py` helper (TDD)
```

but `agent/skills/execute-plan/scripts/extract-plan-tasks.py` only recognized:

```py
^### Task (\d+):\s*(.*)
```

After normalizing headings in memory from `### Task N —` to `### Task N:`, the parser accepted the plan: 7 tasks, 0 errors, waves `[1,3]`, `[2,4]`, `[5,6]`, `[7]`.

### Recommended changes

In `agent/skills/execute-plan/scripts/extract-plan-tasks.py`:

1. Relax task-heading parsing narrowly while keeping generated plans canonical as `### Task N: Title`:

   ```py
   ^### Task (\d+)\s*(?::|—|–|-)\s*(.*)
   ```

   Preserve these constraints:
   - H3 only;
   - literal `Task N`;
   - ordered numeric tasks still enforced;
   - separator still required;
   - only common title punctuation accepted.

2. Improve diagnostics. If the parser sees `^### Task \d+\b` but not an accepted heading shape, emit a targeted error such as:

   ```json
   {"kind": "malformed_task_heading", "line": 52, "heading": "### Task 1 ..."}
   ```

   rather than `missing_required_section: numbered_tasks`.

3. Consider safe section/label leniency where semantics are unambiguous:
   - task labels case-insensitively:
     - `**Files:**`
     - `**Steps:**`
     - `**Acceptance criteria:**` / `**Acceptance Criteria:**`
     - `**Model recommendation:**` / `**Model Recommendation:**`
   - file-scope prefixes case-insensitively (`Create:`, `Modify:`, `Test:` already effectively do this);
   - `Verify:` case-insensitively (`Verify:`, `verify:`), while still requiring exactly one immediately following recipe line per criterion;
   - common top-level required-heading capitalization variants, especially:
     - `## Architecture Summary` / `## Architecture summary`
     - `## Tech Stack` / `## Tech stack`
     - `## Risk Assessment` / `## Risk assessment`

4. Do **not** accept vague aliases such as `## Implementation` for `## Tasks`.

### Tests

Add fixtures/tests under `agent/skills/execute-plan/scripts/tests/` for:

- canonical colon heading accepted: `### Task 1: Title`;
- em dash heading accepted: `### Task 1 — Title`;
- en dash / hyphen accepted if implemented;
- malformed task-like heading produces `malformed_task_heading` rather than `missing_required_section`;
- `**Acceptance Criteria:**` and `**Model Recommendation:**` capitalization variants parse successfully if implemented;
- lowercase `verify:` parses successfully if implemented;
- headings/labels inside fenced code blocks are ignored.

## 2. Provenance preamble: tolerate bold Markdown labels only

`agent/skills/execute-plan/scripts/extract-provenance-preamble.py` consumes human-authored Markdown preambles. It currently accepts plain labels such as:

```md
Source: TODO-12345678
Scout brief: docs/briefs/example.md
Git SHA: <40 lowercase hex chars>
```

Recommendation: also accept the explicit bold-label forms commonly used elsewhere in this repo:

```md
**Source:** TODO-12345678
**Scout brief:** docs/briefs/example.md
**Git SHA:** <40 lowercase hex chars>
```

Preserve strict validation for:

- bounded preamble scanning;
- fence-aware behavior;
- TODO shape (`TODO-<8 lowercase/hex chars>`, unless intentionally changed later);
- scout-brief path shape (`docs/briefs/<file>`);
- 40-character lowercase Git SHA validation in brief mode, including existing `git_sha_malformed` behavior.

Add tests for bold `Source`, `Scout brief`, and `Git SHA` lines, plus fake provenance inside fences.

## 3. Coder reports: accept Markdown heading status, but keep status tokens strict

### Observed failure

During execution of `docs/plans/2026-05-11-2026-05-11-fast-lane-workflow.md`, Task 1 completed substantively but its first report began with:

```md
## STATUS: DONE
```

`agent/skills/execute-plan/scripts/parse-coder-report.py` requires an unfenced line matching `^STATUS:\s*(\S+)`, so it emitted `status_line_missing` and the orchestrator retried solely to obtain a protocol-valid report. The retry did not change the implementation.

### Recommended parser compatibility

Because coder reports are LLM-authored Markdown, allow this narrow form while preserving protocol safety:

```py
^(?:#{1,6}\s+)?STATUS:\s*(DONE|DONE_WITH_CONCERNS|BLOCKED|NEEDS_CONTEXT)\s*$
```

Constraints:

- remain fence-aware;
- status lines inside fenced code blocks must not count;
- keep the status token set strict;
- prefer the first real status line outside fences, as today;
- do not accept prose variants such as `Status is done` or unknown status tokens.

### Prompt hardening

Also tighten worker prompts so protocol-valid output is more likely before parser fallback is needed. For example, in `agent/skills/execute-plan/execute-task-prompt.md` and derived coder prompts, replace generic wording like:

```md
Use this exact structure:
```

with:

```md
Your first non-fenced line MUST be exactly `STATUS: <DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT>` with no Markdown heading marker, bullet, bolding, or preamble. Do not write a summary before the STATUS line.
```

### Tests

Add regression tests for:

- canonical `STATUS: DONE`;
- Markdown-heading `## STATUS: DONE`;
- fake fenced `## STATUS: DONE` ignored;
- unknown status tokens rejected.

## 4. `refine-code`: add deterministic fallback for missing `REVIEW_ARTIFACT` marker

### Observed failure

During execution of `docs/plans/2026-05-11-2026-05-11-fast-lane-workflow.md`, final review stopped with:

```md
STATUS: failed

## Failure Reason
reviewer artifact handoff failed: missing REVIEW_ARTIFACT marker
```

The `code-refiner` reported that a review file existed at:

```text
/Users/david/Code/pi-config/docs/reviews/2026-05-11-2026-05-11-fast-lane-workflow-code-review-v1.md
```

and it had already completed one remediation commit:

```text
c0dab04 fix(review): iteration 1 — baseline comparison contract
```

The `REVIEW_ARTIFACT:` marker is a transport handoff. The on-disk review file plus provenance/verdict validation should remain the source of truth.

### Recommended changes

Do both prompt hardening and a deterministic expected-path fallback.

#### Prompt hardening

In `agent/agents/code-reviewer.md` and `agent/skills/requesting-code-review/review-code-prompt.md`, replace permissive language such as “Conversational text before the marker line is permitted” with a stricter terminal-message contract for refiner-driven reviews:

```md
After writing the review file, your final assistant message MUST be exactly one line:
REVIEW_ARTIFACT: <absolute path>

No summary. No prose. No markdown. No additional lines. This must be the final assistant message.
```

Keep the existing `subagent_done(message="REVIEW_ARTIFACT: <absolute path>")` instruction.

#### Expected-path fallback

If strict parsing with `parse-artifact-handoff.py --marker REVIEW_ARTIFACT ...` fails only because the marker is missing, the coordinator may accept the known expected artifact path only when all deterministic checks pass:

- expected review file exists and is non-empty;
- expected path is exactly the path supplied to the reviewer for this dispatch;
- first non-empty line is byte-equal to the supplied `**Reviewer:** <provider>/<model> via <cli>` provenance line;
- `validate-review-provenance.py --review-file <path> --allowed-tiers <tier>` passes;
- `**Verdict:**` is present and parses as `Approved`, `Approved with concerns`, or `Not approved`;
- artifact freshness is established, e.g. mtime is after dispatch start or file hash/mtime changed from the pre-dispatch snapshot.

If these checks pass, treat the missing marker as a handoff warning and continue using the on-disk file as authoritative. If any check fails, preserve the current hard failure.

Do not broadly relax artifact validation. Keep hard failures for:

- missing/empty expected review file;
- marker present but path mismatches expected path;
- malformed or stale provenance;
- missing/unrecognized verdict;
- stale artifact;
- marker-like text inside quoted/code blocks or anywhere other than the accepted terminal marker path.

Implementation can either:

- keep `parse-artifact-handoff.py` strict and add a refine-code-specific wrapper/helper such as `validate-review-artifact-handoff.py`; or
- add an explicit opt-in mode such as `--allow-missing-marker-if-expected-artifact-valid` with `--expected-path` and freshness checks.

### Tests

Add regression tests for:

- marker present, expected path, valid provenance/verdict → pass;
- marker missing, expected file exists, fresh, valid provenance/verdict → pass with a warning/fallback flag;
- marker missing, expected file missing/empty → fail;
- marker missing, expected file stale → fail;
- marker missing, provenance line differs from supplied reviewer provenance → fail;
- marker missing, verdict missing/unrecognized → fail;
- marker present but path mismatches expected path → fail;
- marker-looking line inside fenced/quoted text does not count as strict handoff marker.

## 5. `generate-plan` / `refine-plan`: safer exhausted-budget user menu

When `generate-plan` runs out of refinement iteration budget while the plan is still not approved, update the menu/settings offered to the user so the choices are explicit and safe.

Recommended behavior:

- Do not present the exhausted-budget state as a normal approved plan handoff.
- Offer clear next actions such as:
  - continue/refine for more iterations;
  - save the current draft as-is for manual review;
  - return to edit the spec/todo inputs before regenerating;
  - abandon/delete the draft plan.
- If the user chooses to continue, make the additional iteration budget explicit before resuming refinement.
- If the user chooses to save/use the draft despite unresolved review findings, label the plan/status accordingly and preserve the latest reviewer concerns in the plan/refinement artifact.
- Avoid defaulting to execution-oriented next steps until the user has explicitly accepted the unapproved draft or continued refinement to approval.

Implement this in the `generate-plan` / `refine-plan` coordination path rather than relying on the model to explain the exhausted-budget state conversationally.

## Out of scope / keep strict by default

Do **not** proactively relax these machine-protocol/artifact parsers unless a concrete failure appears with a safe compatibility story:

- `agent/skills/_shared/scripts/parse-test-runner-artifact.py` — strict headers/counts protect test-run reconciliation correctness.
- `agent/skills/execute-plan/scripts/parse-verifier-report.py` — strict criterion/verdict/evidence format prevents bad verification reports from passing.
- `agent/skills/_shared/scripts/validate-review-provenance.py` — strict provenance gates reviewer model/CLI trust.
- `agent/skills/refine-code/scripts/parse-refine-code-summary.py` — already has targeted leniency for `## Remaining Issues (...)`; keep the rest protocol-oriented.
- `agent/skills/refine-plan/scripts/parse-refine-plan-summary.py` and `validate-and-parse-plan-review.py` — keep strict unless a concrete model-output failure justifies narrow compatibility.

`agent/skills/_shared/scripts/parse-artifact-handoff.py` should also remain strict by default. Any missing-marker acceptance must be explicit and bounded to the expected-path fallback described above.

## Rationale

The known failures were not substantive implementation or planning failures; they were integration-boundary failures caused by minor Markdown drift or fragile transport handoff. Mechanical, narrowly scoped compatibility plus stronger prompts and clearer UX will reduce unnecessary retries/failures without weakening the trust checks that protect execution and review correctness.
