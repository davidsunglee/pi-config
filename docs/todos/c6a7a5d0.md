## Context

Recent `execute-plan` sessions show the main orchestrator repeatedly generating ad hoc Python/bash snippets to perform mechanical orchestration work: parsing plans, filling prompt templates, assembling diffs, extracting protocol markers, and checking artifacts. Some of that generated code is legitimate glue, but recreating it every run is noisy, error-prone, and makes it harder to distinguish allowed mechanical routing from forbidden substantive verification.

This todo complements TODO-5a12e2ea (`Guard execute-plan against ad hoc orchestrator verification`). That todo should prohibit the orchestrator from independently judging implemented work. This todo should extract reusable static helpers for the purely mechanical operations that remain allowed.

## Goal

Add static helper scripts/modules for repeatable, mechanical `execute-plan` orchestration tasks so the main agent does not have to generate custom Python/bash glue every execution.

The helpers must keep a hard boundary: they may assemble inputs, parse structured protocol outputs, and validate protocol shape, but they must not decide whether implementation acceptance criteria pass. Substantive task verification remains the responsibility of `verifier` subagents; integration-test execution and artifact writing remain the responsibility of `test-runner` subagents.

## Recommended helper candidates

### 1. `extract-plan-tasks`

Responsibilities:
- Read a structured plan markdown file.
- Extract task blocks by task number/title.
- Extract each task's `**Files:**` section.
- Extract acceptance criteria and attached `Verify:` recipes.
- Extract dependencies for wave grouping, if useful.
- Report protocol-shape issues mechanically, e.g. missing `Verify:` recipes, missing task sections, duplicate task numbers.

Non-goals:
- Do not judge whether a task implementation satisfies the criteria.
- Do not invent missing criteria or recipes.

### 2. `assemble-coder-prompt`

Responsibilities:
- Fill `agent/skills/execute-plan/execute-task-prompt.md` from structured inputs.
- Include the verbatim task spec.
- Include wave/prior-output/dependency context.
- Include the working directory.
- Include or omit the TDD block based on settings.

Non-goals:
- Do not summarize the task spec in a way that changes requirements.
- Do not decide whether the coder's output is correct.

### 3. `assemble-verifier-prompt`

Responsibilities:
- Fill `agent/skills/execute-plan/verify-task-prompt.md` from structured inputs.
- Include the verbatim task spec.
- Include acceptance criteria paired with planner-authored `Verify:` recipes.
- Include command-style recipes in the Phase 1 recipe section.
- Include the orchestrator-assembled verifier-visible file set.
- Include diff context.
- Include working directory.

Non-goals:
- Do not perform verification locally.
- Do not run `Verify:` commands locally; the `verifier` subagent owns command evidence collection.
- Do not return PASS/FAIL for criteria.

### 4. `collect-diff-context`

Responsibilities:
- Given a working directory and file list, compute verifier-visible diff context mechanically.
- Use `git diff HEAD -- <tracked files>` for tracked modifications.
- Use `git diff --no-index /dev/null -- <file>` for new/untracked files.
- Apply the existing diff truncation rule: keep first 300 lines and last 100 lines with an explicit truncation marker when over the configured line/byte limit.
- Produce a deterministic text block suitable for verifier prompts.
- Optionally output the observed file set from `git status --porcelain` and `git diff HEAD` for prompt assembly.

Non-goals:
- Do not inspect the diff to decide if the implementation is good.
- Do not hide files from the verifier based on the worker's report.

### 5. `parse-verifier-report`

Responsibilities:
- Parse a verifier final message.
- Extract `[Criterion N] PASS|FAIL` entries.
- Detect duplicate, missing, or out-of-range criterion numbers.
- Extract the overall `VERDICT: PASS|FAIL` line.
- Validate Phase 1 evidence-block protocol shape for command-style criteria.
- Return structured parse results and protocol errors.

Non-goals:
- Do not reinterpret malformed output as success.
- Do not decide pass/fail from local evidence; only parse the verifier's declared protocol output.
- Protocol errors may be represented as structured failures for execute-plan routing, but the helper should make clear they are protocol errors, not independent implementation judgments.

### 6. `parse-test-runner-artifact`

Responsibilities:
- Given an expected artifact path, parse and validate the `test-runner` artifact.
- Confirm required headers in exact order.
- Extract `EXIT_CODE`.
- Extract `FAILING_IDENTIFIERS` as a byte-for-byte stable identifier set.
- Extract `NON_RECONCILABLE_FAILURES` as a list of evidence entries.
- Report missing/empty/malformed artifact errors mechanically.

Non-goals:
- Do not run the test command.
- Do not synthesize or write artifacts.
- Do not reconcile against `baseline_failures` unless explicitly scoped as part of a separate integration-gate helper.

### 7. `fill-refine-code-prompt`

Responsibilities:
- Fill `agent/skills/refine-code/refine-code-prompt.md` from known inputs.
- Include plan goal, plan contents, base/head SHAs, working directory, review output path, max iterations, and mode.
- Avoid repeated bespoke Python snippets for building the same prompt.

Non-goals:
- Do not perform review locally.
- Do not inspect the review artifact to decide production readiness beyond mechanical provenance/protocol checks.

### 8. Optional: `fill-refine-plan-prompt`

Responsibilities:
- Fill `agent/skills/refine-plan/refine-plan-prompt.md` from known inputs.
- Include plan path, task artifact/source todo/source spec/scout brief fields, review output path, and model matrix as required by the prompt.

Non-goals:
- Do not perform plan review locally.

## Design constraints

- Helpers should be deterministic and small.
- Prefer plain scripts/modules checked into the repo over per-session heredocs in `/tmp`.
- Inputs and outputs should be explicit enough that the orchestrator can call them without embedding large custom Python snippets.
- Helpers should return structured data where possible, e.g. JSON for parse/extract helpers and plain markdown for prompt assembly helpers.
- Helpers should fail closed on malformed protocol inputs.
- Helpers must not run arbitrary plan-provided commands except where explicitly allowed by their mechanical role. In particular, `collect-diff-context` may call git; `parse-*` helpers should not execute tests or verify recipes.
- Keep helper names and locations discoverable from `agent/skills/execute-plan/SKILL.md`.

## Verification boundary

Allowed helper outputs:
- extracted task metadata;
- filled prompt files/text;
- observed git file/diff context;
- parsed verifier/test-runner protocol records;
- protocol-shape errors;
- bookkeeping/provenance facts.

Forbidden helper outputs:
- `Criterion N passed because grep found X` from local inspection;
- task acceptance PASS/FAIL derived from local grep/Python assertions;
- synthesized `test-runner` artifacts from locally-run tests;
- final acceptance judgments that bypass `verifier` or `test-runner`.

## Relationship to other refactor work

This may be implemented before or alongside the broader execute-plan extraction todo (TODO-b733a4af). Unlike extracting whole skills such as `run-test-artifact` or `verify-implementation`, this todo focuses on static mechanical utilities that reduce per-run generated code while preserving the current high-level execute-plan protocol.

## Acceptance criteria

- `execute-plan` references static helper scripts/modules for at least the highest-noise mechanical tasks instead of generating equivalent heredoc scripts each run.
- The helpers clearly separate mechanical parsing/prompt assembly from substantive verification.
- The helper documentation explicitly says they must not independently judge implementation acceptance criteria.
- Integration-test execution remains routed through `test-runner`; helpers do not run configured test commands or write test-runner artifacts.
- Task verification remains routed through `verifier`; helpers do not run planner-authored `Verify:` recipes or emit implementation PASS/FAIL verdicts.
- Existing execute-plan behavior is preserved except for reducing ad hoc generated glue code.

## Additional helper candidate: `resolve-model-dispatch`

Recent sessions also show repeated ad hoc code for reading `~/.pi/agent/model-tiers.json`, extracting provider prefixes, looking up `dispatch[provider]`, and constructing `(model, cli)` pairs for `coder`, `verifier`, `test-runner`, `refine-plan`, and `refine-code` dispatches.

Responsibilities:
- Read and validate `~/.pi/agent/model-tiers.json`.
- Resolve top-level tiers (`cheap`, `standard`, `capable`) and nested tiers (`crossProvider.cheap`, `crossProvider.standard`, `crossProvider.capable`).
- Extract the provider prefix from `<provider>/<model>`.
- Look up the corresponding CLI in `dispatch[<provider>]`.
- Emit structured output such as `{ "tier": "crossProvider.standard", "model": "...", "provider": "...", "cli": "..." }`.
- Support the existing strict failure cases documented in `agent/skills/_shared/model-tier-resolution.md`, preferably by returning canonical error keys/messages that the orchestrator can surface byte-equal.

Non-goals:
- Do not choose task tiers from task content; tier selection remains execute-plan policy.
- Do not silently fall back to another tier unless the caller explicitly requests a documented fallback chain.
- Do not dispatch subagents itself; this helper only resolves `(model, cli)`.

Estimated savings: **0.5k–2k orchestrator tokens per execute-plan run**, depending on task count and how many coordinator/reviewer/test-runner dispatches occur. It also reduces risk of each session reimplementing model/CLI resolution slightly differently.

## Recommended implementation order and estimated token impact

These estimates are rough and based on recent execute-plan session transcripts. They count avoided orchestrator prompt/code tokens from not generating bespoke heredoc scripts and not repeatedly explaining/parsing the same mechanical protocol in-session. Actual savings scale with task count, wave count, retry count, integration-test usage, and whether final review runs.

| Rank | Helper(s) | Estimated savings per execute-plan run | Explanation |
|---:|---|---:|---|
| 1 | `extract-plan-tasks` | **1.5k–4k tokens** | This is the foundation for most other helpers. The orchestrator repeatedly regex-parses plan markdown for task blocks, files, criteria, recipes, and dependencies. Centralizing this reduces repeated parsing code and gives prompt-assembly helpers structured inputs. |
| 2 | `collect-diff-context` | **1.5k–4k tokens** | Diff assembly is large and error-prone: tracked vs untracked files, `git diff HEAD`, `git diff --no-index /dev/null`, observed file sets, truncation markers, and per-task scoping. It is one of the highest-noise mechanical snippets and runs for verifier dispatches. |
| 3 | `assemble-verifier-prompt` | **1k–3k tokens** | Verifier prompt assembly combines task specs, criteria+recipes, command-style Phase 1 recipes, modified files, diff context, and working directory. It is repeated per task/wave and is the main place where mechanical setup can be confused with forbidden local verification. Best implemented after `extract-plan-tasks` and `collect-diff-context`. |
| 4 | `resolve-model-dispatch` | **0.5k–2k tokens** | Model/CLI resolution appears in many dispatch sites. A small static helper avoids repeated JSON parsing/provider-prefix code and keeps dispatch behavior aligned with `_shared/model-tier-resolution.md`. |
| 5 | `parse-verifier-report` | **0.5k–2k tokens** | The parsing rules are detailed: criterion coverage, duplicates, malformed verdict lines, Phase 1 evidence-block protocol errors, and overall verdict extraction. Savings grow with task count and retries, and the helper reduces risk of the orchestrator improvising verdict parsing. |
| 6 | `parse-test-runner-artifact` | **0.5k–2k tokens when integration tests are enabled** | Useful for baseline, each post-wave test run, debugger re-tests, and final gate. Savings are lower when integration tests are disabled, but high for multi-wave plans with retries. Keeps artifact validation mechanical and prevents the orchestrator from synthesizing artifacts. |
| 7 | `assemble-coder-prompt` | **0.5k–1.5k tokens** | Coder prompt filling is repetitive but simpler than verifier prompt assembly. The full task prompt still has to be sent to the coder, so savings come mostly from eliminating bespoke template-fill code. |
| 8 | `fill-refine-code-prompt` | **0.5k–1.2k tokens** | Usually runs once near the end when final review is enabled. Helpful for consistency and to avoid repeated prompt-building snippets, but not the main execute-plan token hotspot. |
| 9 | `fill-refine-plan-prompt` | **~0 tokens in execute-plan; 0.5k–1k tokens in generate/refine-plan workflows** | Useful elsewhere, but it does not normally reduce execute-plan's own token consumption unless the session also invokes plan refinement. Keep it optional or implement it as part of a shared prompt-filling utility. |

Suggested first slice for maximum value:

1. Implement `extract-plan-tasks` with JSON output.
2. Implement `collect-diff-context` with deterministic text/JSON output.
3. Implement `assemble-verifier-prompt` on top of the first two helpers.
4. Implement `resolve-model-dispatch` because it is small, broadly reused, and reduces dispatch drift.
5. Add `parse-verifier-report` to close the verifier loop mechanically.

This first slice targets the largest observed source of generated code: verifier setup and routing. It also directly supports TODO-5a12e2ea by making it easier for the orchestrator to route verification without performing verification itself.

## Superseding implementation order: shared helpers first, then execute-plan hotspots

This section supersedes the earlier execute-plan-only implementation-order table. Implement broadly reusable helpers in `agent/skills/_shared/` first, then implement the highest-token-savings execute-plan helpers, then fill in the remaining narrower helpers.

### Phase 1 — shared helpers in `agent/skills/_shared/`

1. **`resolve-model-dispatch`**
   - Used by: `define-spec`, `generate-plan`, `refine-plan`, `refine-code`, `execute-plan`.
   - Why first: every dispatch-heavy skill repeats `model-tiers.json` parsing, provider-prefix extraction, and `dispatch[provider]` lookup. This also provides a shared primitive for provenance validation.

2. **`parse-artifact-handoff`**
   - Generic marker/path validator for anchored final-message markers such as:
     - `SPEC_WRITTEN:` (`define-spec`)
     - `REVIEW_ARTIFACT:` (`refine-plan`, `refine-code` coordinator flows)
     - `TEST_RESULT_ARTIFACT:` (`execute-plan` test-runner flow)
   - Responsibilities should include last-marker extraction, expected-path equality, existence/non-empty checks when requested, and structured failure reasons.
   - Why second: several skills already have parallel marker/path validation protocols; centralizing them reduces drift and repeated regex snippets.

3. **`validate-review-provenance`**
   - Used by: `refine-plan`, `refine-code`.
   - Responsibilities: validate first non-empty review line format, reject `inline`, compare model/CLI against allowed tier(s) using `resolve-model-dispatch`, and return precise failure labels.
   - Why third: `refine-plan` and `refine-code` duplicate almost the same reviewer provenance validation logic.

4. **`fill-template`**
   - Generic safe placeholder replacement from a template path plus explicit JSON/key-value inputs.
   - Used by: `generate-plan`, `refine-plan`, `refine-code`, and later execute-plan prompt assembly helpers.
   - Why fourth: many prompt-specific helpers can become thin wrappers around one deterministic template filler.

5. **`extract-provenance-preamble`**
   - Used by: `generate-plan`, `refine-plan`.
   - Responsibilities: bounded preamble reads, exact supported-line extraction, ignoring later document content/fenced examples, and returning structured provenance fields.
   - Why fifth: both skills parse provenance from markdown preambles, but with slightly different supported line shapes.

6. **`classify-workflow-drift`**
   - Mostly used by: `generate-plan`.
   - Responsibilities: use the shared workflow-artifact allowlist, validate scout brief SHA shape/reachability, enumerate `git diff --name-only -z <brief-sha>..HEAD`, classify workflow-only vs mixed drift, and return structured menu/rendering inputs.
   - Why sixth: it is less broadly reused than the first five, but it is complex enough to deserve a static helper and should share the allowlist semantics from `_shared/workflow-artifact-paths.md`.

### Phase 2 — highest execute-plan token savings

7. **`extract-plan-tasks`**
   - Foundation for execute-plan-specific helpers.
   - Estimated execute-plan savings: **1.5k–4k tokens/run**.
   - Why now: verifier/coder prompt assembly and wave routing need structured task blocks, files, criteria, recipes, and dependencies.

8. **`collect-diff-context`**
   - Estimated execute-plan savings: **1.5k–4k tokens/run**.
   - Why now: it removes one of the largest repeated heredoc snippets: tracked/untracked file handling, `git diff HEAD`, `git diff --no-index /dev/null`, observed file sets, and truncation markers.

9. **`assemble-verifier-prompt`**
   - Build on `extract-plan-tasks`, `collect-diff-context`, and `_shared/fill-template`.
   - Estimated execute-plan savings: **1k–3k tokens/run**.
   - Why now: verifier setup is the biggest source of generated orchestration code and the place where mechanical setup most easily blurs into forbidden local verification.

10. **`parse-verifier-report`**
    - Estimated execute-plan savings: **0.5k–2k tokens/run**.
    - Why now: completes the verifier loop mechanically by parsing criterion coverage, duplicates, malformed verdicts, Phase 1 evidence blocks, and overall verdict without improvising.

11. **`parse-test-runner-artifact`**
    - Should reuse `_shared/parse-artifact-handoff` for marker/path checks where applicable.
    - Estimated execute-plan savings: **0.5k–2k tokens/run when integration tests are enabled**.
    - Why now: baseline, post-wave, debugger re-test, and final-gate paths all parse the same artifact structure.

### Phase 3 — remaining execute-plan ergonomics and wrappers

12. **`assemble-coder-prompt`**
    - Build on `extract-plan-tasks` and `_shared/fill-template`.
    - Estimated execute-plan savings: **0.5k–1.5k tokens/run**.
    - Useful, but less urgent than verifier setup because the actual task prompt still has to be sent to the coder.

13. **`fill-refine-code-prompt`**
    - Thin wrapper around `_shared/fill-template` for `agent/skills/refine-code/refine-code-prompt.md`.
    - Estimated execute-plan savings: **0.5k–1.2k tokens/run** when final review is enabled.

14. **`fill-refine-plan-prompt`**
    - Thin wrapper around `_shared/fill-template` for `agent/skills/refine-plan/refine-plan-prompt.md`.
    - Estimated execute-plan savings: **~0 tokens/run** for execute-plan itself, but **0.5k–1k tokens/run** in generate/refine-plan workflows.

15. **Optional: `parse-refine-plan-summary` / `parse-refine-code-summary`**
    - Parse compact coordinator summaries (`STATUS`, `COMMIT`, `PLAN_PATH`, `REVIEW_PATHS`, `FAILURE_REASON`, review file paths, iteration counts).
    - Lower urgency, but helpful for reducing repeated status parsing and making caller behavior deterministic.
