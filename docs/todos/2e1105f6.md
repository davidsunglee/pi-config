## Problem

`define-spec` has two observed workflow failures:

1. Passing a todo such as `TODO-bd750b75` to `/define-spec` can cause the interactive `spec-designer` subagent to ask what it is designing instead of recognizing the todo as a pointer to `docs/todos/<raw-id>.md`.
2. The handoff from `spec-designer` back to the orchestrator is unreliable; the orchestrator may have to search/recover the written spec artifact instead of receiving a clean path.

## Verified root causes / evidence

### 1. The spec-design procedure is not actually reaching `spec-designer`

`define-spec` intends to dispatch `spec-designer` with the full procedure as per-call `systemPrompt`:

- `agent/skills/define-spec/SKILL.md` dispatches `task: <raw user input>` and `systemPrompt: <full spec-design-procedure.md>`.
- `agent/skills/define-spec/spec-design-procedure.md` contains the todo detection table. It says exact `TODO-([0-9a-f]{8})` should read `docs/todos/<raw-id>.md` and set `Source: TODO-<raw-id>`.

But the `pi-interactive-subagent` launcher currently resolves identity as:

```ts
const identity = agentDefs?.body ?? params.systemPrompt ?? null;
```

in `/Users/david/Code/pi-interactive-subagent/pi-extension/subagents/launch-spec.ts`.

Because `agent/agents/spec-designer.md` has a non-empty body and `system-prompt: append`, the per-call `systemPrompt` procedure is dropped. The subagent therefore sees only the base `spec-designer` identity and not the procedure's input-shape detection. This explains why it treats a todo as freeform and asks what to design.

Secondary fragility: the procedure's todo regex is exact and narrow. These fall through as freeform today:

- `bd750b75`
- `TODO-BD750B75`
- `/define-spec TODO-bd750b75`
- `define spec for TODO-bd750b75`
- `TODO-bd750b75 `

### 2. Artifact handoff is specified but not robust on the Claude pane path

The procedure says the final assistant message must contain:

```text
SPEC_WRITTEN: <absolute path>
```

and `define-spec` parses `results[0].finalMessage` for that marker.

However current model tiers resolve `capable` for `spec-designer` to Claude CLI, and Claude pane completion uses `subagent_done`. The MCP `subagent_done` tool accepts an optional `message`; the watcher prefers the sentinel message over the transcript's last assistant message:

- `/Users/david/Code/pi-interactive-subagent/pi-extension/subagents/plugin/mcp/server.ts` accepts optional `message` and writes it to the sentinel.
- `/Users/david/Code/pi-interactive-subagent/pi-extension/subagents/index.ts` reads sentinel text first and uses it as the final summary/finalMessage.

So if Claude calls `subagent_done(message="Wrote the spec.")`, the parent sees `finalMessage = "Wrote the spec."` even if the previous assistant message included `SPEC_WRITTEN: ...`. The integration test pins the safer pattern (`subagent_done with message="SPEC_WRITTEN: <path>"`), but `define-spec`'s actual procedure only tells the subagent to send a final assistant message, not to pass the marker as the `subagent_done.message` payload.

## Other inconsistencies / risk areas

- Repo skill uses `agent/skills/define-spec/spec-design-procedure.md`; installed global copy uses `/Users/david/.pi/agent/skills/define-spec/procedure.md`. Contents matched during investigation, but the naming drift can cause edits to miss runtime.
- Direct marker validation calls `parse-artifact-handoff.py --check-existence` but not `--check-non-empty`, even though error text says "missing or empty".
- Direct marker validation does not constrain the path to `docs/specs/*.md`; transcript recovery does.
- Transcript recovery is prose only, not a deterministic helper, so the orchestrator may improvise parsing successful write/edit evidence.
- Existing-spec branch says to overwrite the input path verbatim, while Step 9 requires emitting an absolute path. Relative `docs/specs/foo.md` refinement is underspecified.
- `detect-mux-backend.py` treats any occurrence of substring `inline` in user input as an inline override, which may false-positive when the requested work mentions inline behavior.

## Proposed solution

1. Fix per-call system prompt composition in `pi-interactive-subagent` so `system-prompt: append` actually combines the agent body and per-call `params.systemPrompt` instead of dropping one.
   - Preserve `system-prompt: replace` behavior intentionally.
   - Add/update tests that dispatch an agent with body + per-call systemPrompt and verify both reach the child.
2. Harden `define-spec`'s Claude-pane completion instructions.
   - Tell Claude-backed `spec-designer` to call `subagent_done(message="SPEC_WRITTEN: <absolute path>")` or otherwise ensure the parent-facing `finalMessage` contains exactly the marker line.
   - Keep the final assistant marker requirement for Pi-backed children.
3. Tighten direct `SPEC_WRITTEN` validation.
   - Require non-empty file content (`--check-non-empty`).
   - Require the path to normalize under the current repo's `docs/specs/` and end in `.md`.
   - Consider extracting this validation/recovery into a deterministic helper instead of prose-only transcript recovery.
4. Decide whether todo input detection should remain exact or accept common slash-command/raw-id variants; document and test whichever behavior is desired.
5. Normalize the procedure filename/copying story between repo and installed global config so runtime and source stay aligned.

## Acceptance criteria

- `/define-spec TODO-<8hex>` in mux/Claude-pane mode causes `spec-designer` to read `docs/todos/<raw-id>.md` before asking spec-content questions.
- A regression test proves `spec-designer` receives the full spec-design procedure when launched with an agent body and per-call `systemPrompt`.
- Successful mux runs return a parent-visible `results[0].finalMessage` containing `SPEC_WRITTEN: <absolute path>` without requiring transcript recovery.
- The orchestrator rejects missing, empty, non-md, or outside-`docs/specs/` handoff paths before the review/commit gate.
- Existing-spec refinement with relative and absolute `docs/specs/*.md` paths has explicit, tested path behavior.
- Any remaining transcript-backed recovery is deterministic, narrow, and tested; it never scans for the newest spec file or guesses from filesystem state alone.
- Documentation/tests cover the accepted todo input forms and reject/handle unsupported forms clearly.
