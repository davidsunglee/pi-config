## Context

While validating `docs/plans/2026-05-09-harden-workflow-parsers-against-markdown-like-content-in-embedded-payloads.md`, the deployed `~/.pi/agent/skills/execute-plan/scripts/extract-plan-tasks.py` reported missing `## Dependencies` and `## Risk Assessment` sections even though they were present.

Root cause: the plan contained outer triple-backtick example fences that themselves included inner triple-backtick fences. The current fence scanner treated an inner fence as the closer for the outer fence, then later treated the real outer closer as a new opener that ran to EOF. That made later top-level sections invisible to validation.

We patched the specific plan locally by changing the affected outer example fences to `~~~`, which validates cleanly against both the deployed script in `~/.pi/agent` and the repo copy.

## Problem

Plan-writing flows can emit ambiguous fenced examples that are invalid or misleading for the downstream lightweight parser. When that malformed pattern appears, validation currently fails with a misleading missing-section error instead of identifying the actual fence ambiguity.

## Scope

Limit this todo to two pieces of work:

1. **Generation-side hardening**
2. **Validation-side targeted failure reporting**

Apply the generation-side protection to both:
- initial `generate-plan` output
- `refine-plan` edits / rewritten plan content

## Desired behavior

### 1. Prevent ambiguous fenced examples in generated/refined plans

Add a deterministic safeguard in the plan-writing path so emitted plan text uses unambiguous outer fences for embedded examples or prose blocks.

Fence rule:
- outer fences must be unambiguous relative to their payload
- prefer `~~~` when embedding triple backticks
- otherwise, a same-marker outer fence is only allowed when its length is strictly longer than any same-marker run inside the payload

Prompt guidance may reinforce this rule, but prompt wording alone is not sufficient; the emitted artifact should be checked or normalized deterministically.

### 2. Fail precisely when malformed ambiguous fences still appear

Teach the validator to detect ambiguous same-marker nested fences in plan prose/examples and **hard-fail** with a dedicated machine-readable error code.

Requirements for that failure mode:
- keep the surrounding response shape stable
- replace misleading `missing_required_section`-style failures for this case with a specific fence-ambiguity classification
- include a clear remediation hint such as switching the outer fence to `~~~` or using a longer same-marker fence

## Non-goals

Do **not** include the following in this todo:
- a separate preflight lint pass in `generate-plan`, `refine-plan`, or `execute-plan`
- best-effort parser recovery or continuation after detecting this malformed case
- auto-rewriting already-written malformed plans as part of validation
- rollout/proof for the deployed `~/.pi/agent` copy

## Acceptance criteria

- `generate-plan` and `refine-plan` plan-writing paths produce unambiguous outer fences for embedded fenced examples.
- The generation-side safeguard is deterministic rather than relying only on prompt instructions.
- The validator detects ambiguous same-marker nested fences in plan prose/examples and fails with a dedicated machine-readable error code plus a clear remediation hint.
- The existing validator response structure remains compatible aside from the new specific error classification/message.
- In-repo regression tests cover:
  - the ambiguous triple-backtick example case
  - a safe `~~~` outer-fence case
  - a longer same-marker outer-fence case
  - targeted failure reporting for malformed ambiguous input

## Expected outcome

Newly generated or refined plans should no longer emit this malformed fence pattern. If an older or manually edited plan still contains it, validation should fail with a precise protocol error instead of a misleading missing-section error.
