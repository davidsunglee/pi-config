## Summary

`define-spec` Step 8 currently delegates the post-commit workflow recommendation to `agent/skills/fast-lane/scripts/recommend-workflow.py`. That helper is too shallow and treated as more authoritative than it should be for an advisory, user-overridable menu choice.

It recommended fast lane for TODO-40e342b9 / `docs/specs/2026-05-11-harden-workflow-boundaries.md`, even though that work clearly merits `generate-plan` → `execute-plan` because it spans multiple workflow skills, parsers, artifact handoffs, trust-boundary validation, prompt contracts, and exhausted-budget UX.

Current helper behavior is essentially:

- recommend fast lane when there is no `## Approach` section;
- requirements bullet count is below a threshold;
- `## Non-Goals` lacks a few flagged keywords.

This misses the actual judgment needed: surveyed-file breadth, structured/numbered requirements, acceptance-criteria volume, trust/provenance/freshness semantics, parser/protocol boundaries, and cross-skill orchestration risk.

## Goal

Replace the shallow script-driven recommendation with an LLM-native Step 8 recommendation flow in `agent/skills/define-spec/SKILL.md`.

After the spec is committed, the orchestrating agent should read the committed spec, make a contextual recommendation between fast lane and deep workflow, explain the recommendation briefly and truthfully, and still let the user override it.

## Recommended design

Change Step 8 from “invoke `recommend-workflow.py` and render its JSON result” to “read the committed spec and make an advisory judgment.”

The Step 8 instructions should direct the orchestrator to:

1. Read the committed spec into context.
2. Assess whether the work is better suited to:
   - **fast lane** — checklist, serial execution, essential gates; or
   - **deep workflow** — `generate-plan` → `execute-plan`, dependency decomposition, parallel execution, verifier/reconciliation gates.
3. Recommend one option with a concise rationale.
4. Make clear the user can override the recommendation by choosing either menu option.

The recommendation should be based on real scope and risk signals from the spec, not only superficial markdown counts.

## Recommendation guidance for Step 8

Recommend **deep workflow** when the spec indicates any of the following:

- multiple workflow skills, agents, or subsystems are affected;
- parser, protocol, artifact-handoff, provenance, trust-boundary, or freshness semantics are involved;
- fallback, validation, migration, security, compatibility, or orchestration behavior is changing;
- git, commit, worktree, branch-completion, or workflow-boundary behavior is affected;
- requirements or acceptance criteria span several independent concerns;
- implementation likely needs dependency decomposition, parallelizable work, verifier gates, or integration reconciliation;
- the agent is uncertain whether fast lane is sufficient.

Recommend **fast lane** when the spec is clearly localized and low risk:

- likely 1–3 files or one narrow subsystem;
- small requirement and acceptance surface;
- no cross-skill, multi-agent, parser/protocol, provenance/trust, or orchestration semantics;
- no broad compatibility or migration concerns;
- a single coder plus standard tests/refinement is likely enough.

## Treatment of `recommend-workflow.py`

`recommend-workflow.py` should no longer be the authoritative recommender for Step 8.

Implementation may either:

- remove the Step 8 dependency on the script and delete the script/tests if nothing else uses it; or
- keep/demote the script as a non-authoritative signal extractor or compatibility helper, as long as Step 8 does not blindly follow its output.

If the script remains, its output should be treated as optional supporting evidence only. The orchestrating LLM’s spec-based judgment owns the final recommendation text.

## Step 8 menu behavior

Keep the menu simple:

```text
Spec committed at <path>. Recommended next step: <fast lane | deep workflow> because <rationale>.

Options:
(f) fast lane     — use checklist, serial execution, essential gates
(d) deep workflow — run full plan, parallel execution, all gates
(x) stop          — leave the workflow for later
```

Routing remains:

- `(f) / fast / fast lane` → invoke `/fast-lane <spec-path>`.
- `(d) / deep / deep workflow / generate-plan` → invoke `/generate-plan <spec-path>`.
- `(x) / stop / no` → exit silently; the spec remains committed.

Also fix the current stale Step 8 copy that says stop will “leave spec uncommitted for later”; by Step 8 the spec has already been committed.

- Step 8 explicitly instructs the orchestrator to read the committed spec before recommending fast lane vs deep workflow.
- Step 8 documents the advisory nature of the recommendation and preserves user override routes for both options.
- Step 8 recommends deep workflow for specs involving cross-skill, parser/protocol, artifact-handoff, provenance/trust/freshness, validation/fallback, git/workflow-boundary, or broad orchestration semantics.
- Step 8 recommends fast lane only for clearly localized, low-risk work.

- Existing tests for `recommend-workflow.py` are removed or updated to match its new role if the script is kept.
- The Step 8 stop-option wording is corrected so it does not imply the already-committed spec is uncommitted.
