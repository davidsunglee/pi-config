# Goal
Configure Agent Safehouse as the practical daily-driver sandbox layer for Pi on macOS, especially for native iOS/Xcode work, without creating a separate repo initially.

This is distinct from `pi-gondolin-sandbox` (microVM-backed Pi tool execution) and `claude-srt-launcher` (SRT-backed Claude Code launcher). Safehouse should be managed from `pi-config`/dotfiles as local wrapper scripts and policy overlays unless it grows into reusable package-level implementation.

# Recommended scope
Add a small Safehouse configuration area to `pi-config`, likely:

```text
safehouse/
  README.md
  bin/
    pi-safe
    pi-ios
    pi-ios-debug
  profiles/
    pi-local-overrides.example.sb
    pi-strict-deny.example.sb
  smoke/
    pi-safehouse-smoke.sh
```

Machine-specific live files should stay outside the repo, e.g.:

```text
~/.config/agent-safehouse/pi-local-overrides.sb
~/.local/bin/pi-safe -> /Users/david/Code/pi-config/safehouse/bin/pi-safe
~/.local/bin/pi-ios -> /Users/david/Code/pi-config/safehouse/bin/pi-ios
~/.local/bin/pi-ios-debug -> /Users/david/Code/pi-config/safehouse/bin/pi-ios-debug
```

# Wrapper behavior
Create convenience wrappers around Safehouse:

- `pi-safe`: daily Pi under Safehouse with the current directory as workdir.
- `pi-ios`: Pi under Safehouse with `--enable=xcode` for Xcode builds, Simulator, `xcodebuild`, `simctl`, `devicectl`, SwiftPM/Xcode cache state, etc.
- `pi-ios-debug`: Pi under Safehouse with `--enable=xcode,lldb` only for debugger/task-port workflows.

Suggested baseline shape:

```bash
safehouse --workdir="$PWD" --append-profile="$HOME/.config/agent-safehouse/pi-local-overrides.sb" -- pi "$@"

safehouse --workdir="$PWD" --enable=xcode --append-profile="$HOME/.config/agent-safehouse/pi-local-overrides.sb" -- pi "$@"

safehouse --workdir="$PWD" --enable=xcode,lldb --append-profile="$HOME/.config/agent-safehouse/pi-local-overrides.sb" -- pi "$@"
```

Wrappers should handle missing local override files gracefully or install a template.

# Policy guidance
Use Safehouse defaults as the baseline:

- The selected invocation directory is read/write.
- Safehouse does not automatically widen from a nested directory to the enclosing Git repo; broaden explicitly with `--add-dirs` or `--add-dirs-ro` only when needed.
- Home directory access is not recursive by default; Safehouse grants metadata/root traversal plus narrow config/cache discovery.
- Existing linked worktrees are read-only visible when launched from a worktree root.
- Network is open by default in Safehouse; treat it as filesystem/process hardening, not egress prevention.

Default-deny/avoid optional integrations unless the current task requires them:

- Do not enable `docker` by default.
- Do not enable `ssh` by default.
- Do not enable `cloud-credentials` by default.
- Do not enable `keychain` by default.
- Do not enable `clipboard` by default.
- Do not enable `wide-read` by default.
- Do not enable `process-control` or `lldb` except for debugging.
- Do not use `--trust-workdir-config` in untrusted repositories.

Use explicit one-off flags for special cases:

- `--add-dirs-ro=/path/to/shared-lib` for read-only context.
- `--add-dirs=/path/to/repo-root` only when a nested launch needs full repo write access.
- `--env-pass=NAME1,NAME2` for selected env vars; avoid `--env` because it passes the full host environment, including secrets.

# Dedicated macOS user recommendation
Safehouse should ideally run under a dedicated macOS user such as `pi-agent` for daily Pi work.

Reason: Safehouse's built-in Pi profile grants access to `~/.pi`, including Pi auth/config/session state. A dedicated user reduces exposure to the primary user's keychain, browser profiles, SSH keys, documents, and personal cloud credentials before Safehouse policy is even considered.

# Xcode/iOS recommendation
For ordinary native Apple work:

- Use `pi-ios` (`--enable=xcode`).
- This grants Xcode developer roots and per-user Xcode/CoreSimulator/CoreDevice/SwiftPM cache state needed by `xcodebuild`, Simulator tooling, and SwiftPM.
- Do not include `lldb` by default; reserve `pi-ios-debug` for actual debugger/task-port workflows.

For high-risk native Apple work:

- Escalate to a Tart macOS VM rather than relying only on Safehouse.

# Network caveat
Safehouse intentionally allows network by default. It is not the right layer for strong egress control.

For medium-risk local work, pair Safehouse with LuLu/Little Snitch/pf if outbound visibility/control is needed.

For high-risk Linux-compatible work, use Gondolin instead.

For high-risk native Apple work, use Tart.

# Relationship to other sandbox work
- Keep this in `pi-config` initially; no dedicated repo is needed yet.
- `pi-gondolin-sandbox` remains the reusable repo/package for Gondolin-backed Pi tool execution.
- `claude-srt-launcher` remains the reusable repo/package for SRT-backed Claude Code policies.
- If Safehouse configuration grows into reusable install/bootstrap/profile tooling used outside `pi-config`, reconsider a dedicated repo later.

# Documentation deliverables
Document:

- When to use `pi-safe`, `pi-ios`, `pi-ios-debug`.
- Which Safehouse `--enable` features are intentionally not enabled by default.
- How to add read-only context paths safely.
- How to add temporary writable paths safely.
- How to pass selected environment variables safely.
- Why `--env`, `wide-read`, Docker socket, cloud credentials, SSH agent, clipboard, keychain, and lldb are all opt-in.
- Why Safehouse is not a VM boundary.
- When to escalate to Gondolin or Tart.

# Smoke tests / acceptance criteria
- Safehouse is installed or installation instructions are documented.
- `pi-safe --version` or equivalent starts Pi under Safehouse.
- A smoke command verifies Pi can read/write in the selected workdir.
- A smoke command verifies a file outside the workdir cannot be read by default.
- `pi-ios` can at least run a harmless Xcode-related command such as `xcodebuild -version` or `xcrun simctl list` under Safehouse.
- `pi-ios-debug` is documented but not used by default.
- Local override profile template exists and can be copied to `~/.config/agent-safehouse/pi-local-overrides.sb`.
- No separate repo is created unless future scope justifies it.
