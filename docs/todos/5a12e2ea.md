## Context

During execute-plan, after coder subagents complete work, the orchestrator should not invent ad hoc verification instructions, run spot checks, or otherwise verify coder output itself. Plans already contain acceptance criteria and `Verify:` recipes produced ahead of time by the planner. Execute-plan is supposed to route verification through dedicated `verifier` subagents using the prescribed verifier prompt/template and parsed verdict protocol.

## Problem

The current execute-plan procedure leaves room for the main orchestrator to pollute its context by doing local/ad hoc verification between coder completion and official verifier dispatch. This duplicates the verifier role, risks inconsistent criteria, and undermines the purpose of planner-authored verification recipes.

## Desired behavior

- Add explicit guardrails to the execute-plan skill/procedure: after coder subagents return, the orchestrator must not perform ad hoc spot checks or invent verification criteria.
- The orchestrator may only perform mechanical routing/parsing tasks required by the protocol, such as collecting worker reports, assembling declared file/diff context, checking plan protocol requirements, dispatching verifiers, and parsing verifier outputs.
- All substantive verification of coder work must be performed by dedicated `verifier` subagents against the plan's acceptance criteria and `Verify:` recipes.
- Make the prohibition prominent near Step 9/Step 11, where the temptation to spot-check coder output is highest.

## Exploration for refinement

Investigate whether parallel coder dispatch should be nested inside serial subagent orchestration calls that pair each coder with its verifier back-to-back (coder → verifier), since verification is known to follow coding. Explore whether this improves protocol discipline, context isolation, and orchestration simplicity, and whether it fits the existing wave-level gating model.

## Acceptance criteria

- execute-plan documentation explicitly forbids orchestrator ad hoc verification/spot checks after coder work.
- The allowed orchestrator responsibilities are limited to mechanical protocol work and verifier dispatch/parsing.
- The todo refinement explores coder+verifier serial pairing as a possible design, without assuming it is definitely the right implementation.

## Specific guardrail recommendations from session review

Recent execute-plan sessions show two distinct classes of orchestrator-generated code:

1. **Allowed mechanical glue** — acceptable for the orchestrator, though it may later be extracted into static helper scripts:
   - filling `coder`, `verifier`, `test-runner`, `refine-plan`, and `refine-code` prompt templates;
   - extracting task blocks, acceptance criteria, and `Verify:` recipes from plan markdown;
   - resolving model tiers and dispatch CLIs from `~/.pi/agent/model-tiers.json`;
   - assembling verifier-visible file sets from declared task scope, worker reports, and git status/diff;
   - generating diff context for verifier prompts, including no-index diffs for new files and truncation markers;
   - parsing verifier/test-runner protocol markers and verdicts;
   - doing completion bookkeeping such as moving plans, checking review artifact provenance, closing linked todos, and checking git status.

2. **Forbidden substantive verification** — the main orchestrator must stop doing this after coder work:
   - writing Python/grep/assertion scripts that independently check acceptance criteria;
   - running spot checks against implemented files to decide whether criteria pass;
   - creating “final acceptance” scripts that re-check task-specific expected strings, headings, paths, todo body contents, review verdicts, or implementation behavior;
   - directly running the integration test command instead of dispatching the `test-runner` subagent;
   - writing test-runner artifacts itself from locally-run test output;
   - interpreting local command output as evidence that a task passed, except when merely parsing a verifier/test-runner artifact produced by the relevant subagent.

Recommended execute-plan wording:

> After a coder returns `DONE` or `DONE_WITH_CONCERNS`, the orchestrator MUST NOT run local grep/Python/assertion scripts, spot checks, or final acceptance checks to decide whether the implementation satisfies the task. The only sanctioned path for substantive task verification is dispatching a fresh `verifier` subagent with the planner-authored acceptance criteria and `Verify:` recipes, then mechanically parsing the verifier's protocol output. The orchestrator may assemble prompt inputs and parse protocol markers, but it must not independently judge the work.

Recommended integration-test wording:

> The orchestrator MUST NOT run the configured test command itself and then synthesize a test-runner artifact. All integration-test execution and artifact writing must be performed by the `test-runner` subagent. The orchestrator may only create the parent directory, dispatch `test-runner`, read back the artifact path marker, validate the artifact format, and reconcile parsed results against the frozen baseline.

Potential static helper scripts should be limited to mechanical operations only. Good candidates include `extract-plan-tasks`, `assemble-coder-prompt`, `assemble-verifier-prompt`, `collect-diff-context`, `parse-verifier-report`, `parse-test-runner-artifact`, and `fill-refine-code-prompt`. These helpers should not return pass/fail judgments for implementation criteria; judgment remains with `verifier` and `test-runner`.
