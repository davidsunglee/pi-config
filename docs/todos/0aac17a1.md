## Summary

Design a scaled-down implementation workflow for small features and bug fixes that keeps the same front door as the current heavyweight workflow: `define-spec`.

The key reframing: fastlane should **not** mean "skip requirements shaping and jump from a raw task description to code." The interactive `define-spec` stage is valuable because it is where the user has a deep Q&A with the LLM and can provide intent, context, constraints, and implementation preferences. Fastlane should branch **after** a spec exists, replacing the heavyweight `generate-plan` → `refine-plan` → `execute-plan` path with a compact path:

1. read the committed spec,
2. produce a lightweight implementation checklist,
3. dispatch a single `coder` subagent to implement it,
4. run targeted verification,
5. dispatch an independent `code-reviewer` for a one-pass review,
6. fix only blocking review findings,
7. commit, and optionally push directly from the current branch/HEAD when the user explicitly wants that.

This matches the ad hoc workflow that has been working well for small changes, but makes it first-class and repeatable.

## Current workflow context

The repository's current workflow is intentionally rigorous for medium-to-heavy work:

- `define-spec` performs interactive spec shaping, via `spec-designer` in a mux pane when available or inline otherwise. It writes `docs/specs/*.md`, gates user review/commit, and currently offers `generate-plan` as the only next step.
- `generate-plan` dispatches `planner`, writes a structured plan under `docs/plans/`, then hands off to `refine-plan` for an adversarial review/edit loop and plan-artifact commit gate.
- `execute-plan` validates the structured plan, optionally creates/reuses a worktree, decomposes tasks into dependency-ordered waves, dispatches `coder` subagents in parallel, verifies each task with fresh-context `verifier` agents, makes checkpoint commits, runs integration tests through `test-runner` before and after changes using baseline/regression reconciliation, invokes `refine-code`, performs a final integration gate, closes linked todos, and optionally finishes the branch.
- `refine-code` drives a multi-iteration code review/remediation loop through a `code-refiner` coordinator, `code-reviewer`, and remediator `coder` subagents.
- `requesting-code-review` already provides a standalone one-pass `code-reviewer` dispatch over an explicit git range and requirements context.
- `commit`, `test-driven-development`, `verification-before-completion`, and `receiving-code-review` provide reusable discipline that should survive in a lighter path.

That stack is appropriate for multi-file, multi-concern, dependency-heavy work. It is excessive for a one-subsystem bug fix, a small behavior tweak, a small config/UX change, or a narrowly scoped refactor.

## Motivation

- The full pipeline can dispatch many subagents: planner, plan reviewers/editors, parallel coders, verifiers, test-runners, code reviewers/remediators, and branch-finish helpers. A 20-line bug fix does not need that machinery.
- Fresh-context subagents are valuable but expensive. Fastlane should spend them where they matter most for small work: one implementation pass and one independent review pass.
- The full pipeline's wave model assumes meaningful decomposition and dependencies. Small tasks are usually one coherent unit.
- The full integration baseline/final-gate model is excellent for large plans, but running the whole suite twice before/after every small task is often unnecessary. Targeted verification plus reviewer scrutiny is usually enough, with escalation when confidence is low.
- Users already run a version of this manually: ask for a lightweight task list, send it to a coder subagent, ask for a code review, fix blocking issues, then commit/push. The repo should encode that as an intentional workflow instead of leaving it as an implicit workaround.

## Proposed workflow

### 1. Keep `define-spec` as the entry point

For small features and non-trivial bug fixes, start with `/define-spec` just as the full workflow does. This preserves the deep Q&A and creates a durable requirements artifact.

After the spec is committed, change `define-spec`'s continuation prompt from a binary `generate-plan?` offer to a route-selection prompt, for example:

```text
Spec committed at <path>. Recommended next step: <fastlane|full plan> because <short rationale>.

Options:
(f) Fastlane — lightweight checklist + one coder + one review
(p) Full plan — generate-plan/refine-plan/execute-plan
(x) Stop — leave the spec committed for later
```

The recommendation should be heuristic and user-overridable. The user can still choose the full pipeline for a small task or fastlane for a task the agent thinks is small-but-not-tiny.

### 2. Add a `fastlane` skill as the post-spec execution path

Prefer a new `agent/skills/fastlane/` skill over embedding this as a mode inside `execute-plan`.

Rationale:

- `execute-plan` is now highly specialized around structured plan parsing, wave scheduling, verifier boundaries, test-runner artifacts, and final cleanup. A fastlane branch inside it would either inherit too much heavyweight ceremony or introduce many conditional paths.
- A separate skill can be short and explicit, while still reusing shared helpers, model-tier resolution, `coder`, `code-reviewer`, `commit`, TDD guidance, and verification discipline.
- `define-spec` can offer `fastlane <spec-path>` as a sibling to `generate-plan <spec-path>`.

The skill should accept a spec path as its primary input. It may also accept a todo/freeform input for explicitly trivial cases, but the recommended/default route is `define-spec` → `fastlane`.

### 3. Lightweight planning/checklist phase

The orchestrator reads the spec and enough code to ground the work, then produces a short implementation checklist for user confirmation. This is intentionally not a full `docs/plans/` artifact unless the design later decides an audit trail is worth the overhead.

The checklist should include:

- goal summary,
- expected file/subsystem touch points,
- 3-7 implementation steps,
- test/TDD plan,
- verification commands to run after implementation,
- escalation risks that would trigger the full pipeline.

The user gets a small checkpoint:

```text
Proceed with this fastlane checklist? (s)tart / (e)dit / (p)romote to full plan / (x) stop
```

### 4. Single implementation subagent

Dispatch one `coder` subagent with a self-contained prompt containing:

- the spec path and relevant spec content or summary,
- the lightweight checklist,
- expected files/subsystems,
- TDD instructions when the change is behavioral or a non-trivial bug fix,
- required verification commands,
- the same `STATUS: DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED` reporting contract already used by plan execution.

Default model tier should likely be `standard`, with `cheap` allowed for very small mechanical changes and `capable` for small-but-subtle work. Resolve concrete `(model, cli)` through `model-tiers.json`, not agent defaults.

### 5. Verification scaled to scope

Fastlane keeps `verification-before-completion`, but does not automatically run the full `test-runner` baseline/final-gate protocol.

Minimum verification:

- run the targeted tests/checks named in the checklist or discovered during implementation,
- for bug fixes, prefer a failing regression test first when practical,
- read the command output before claiming success,
- run the broader project check only when the touched area or risk warrants it.

If tests cannot be run, output is ambiguous, or failures may be pre-existing but cannot be distinguished, escalate or ask the user rather than silently proceeding.

### 6. One independent review pass

After verification, capture `BASE_SHA` before implementation and `HEAD_SHA` after implementation, then dispatch an independent `code-reviewer` over `BASE_SHA..HEAD_SHA` with the spec/checklist as requirements context.

Review gate:

- `Approved` → proceed to commit.
- `Approved with concerns` → proceed if the reviewer explicitly waived all Important findings as non-blocking; record the concerns in the final summary or follow-up.
- `Not approved` → fix Critical findings and any Important findings the reviewer treats as mandatory before commit.
- Minor findings never block, though they may be fixed opportunistically.

This should be a one-pass review by default, not the full `refine-code` loop. If the reviewer returns `Not approved`, do one targeted remediation pass through `coder` and then re-review the remediation or full range. If the second review is still `Not approved`, stop and recommend `refine-code` or the full plan workflow.

Design note: decide whether fastlane should reuse `requesting-code-review` as-is, extend it to support persisted review artifacts/cross-provider tier selection, or dispatch `code-reviewer` directly with the existing `review-code-prompt.md` and a fastlane-specific output path under `docs/reviews/`.

### 7. Commit, optional push, and todo closure

After verification and review pass:

- invoke the `commit` skill with the intended paths or full diff, using Conventional Commits style;
- do **not** push unless the user explicitly requested push behavior for this run;
- if the spec has `Source: TODO-<id>`, close or update the todo after a successful commit, appending a note such as `Completed via fastlane: <commit SHA>, spec: <path>`;
- when pushing directly on HEAD/current branch, surface the branch name and require explicit confirmation.

Fastlane should allow direct work on the current branch by default, because avoiding worktree setup is one of its speed advantages. It still needs a git preflight:

- capture `BASE_SHA` before changes,
- show `git status --porcelain`,
- refuse to mix with unrelated dirty changes unless the user explicitly confirms the intended file set,
- warn when committing directly to `main`/`master`/`develop`.

## Fit criteria

Fastlane is a good fit when the spec describes:

- one coherent change in one subsystem,
- a localized bug fix or small feature,
- an expected diff that is easy to review as one unit,
- no meaningful dependency graph between tasks,
- verification that can be expressed as a small set of targeted tests/checks,
- no unresolved architectural choice after `define-spec`.

Prefer the full `generate-plan`/`execute-plan` workflow when the work involves:

- multiple independent subsystems,
- a broad interface or protocol change,
- migrations, security-sensitive changes, concurrency, data-loss risk, or compatibility concerns,
- many files or unknown blast radius,
- staged rollout / ordering dependencies,
- multiple parallelizable tasks,
- ambiguous acceptance criteria that need verifier-style per-criterion enforcement,
- flaky or already-failing integration tests where baseline reconciliation matters.

Escalation triggers during fastlane:

- the lightweight checklist grows into more than one coherent unit of work,
- the code survey reveals broader scope than the spec implied,
- the coder returns `BLOCKED` or repeatedly needs context,
- verification requires broad integration-test reconciliation,
- review returns `Not approved` after one remediation/re-review cycle,
- the user loses confidence and wants the full process.

Escalation should stop fastlane cleanly and offer `generate-plan <spec-path>` using the same spec artifact. Do not attempt to auto-convert ad hoc checklist state into a structured plan unless that behavior is designed explicitly.

## Guardrails retained vs. intentionally dropped

Retain:

- `define-spec` Q&A and user review/commit gate.
- TDD for behavioral changes and non-trivial bugs, scaled to task size.
- Verification-before-completion with real command output.
- Fresh-context implementation (`coder`) and fresh-context review (`code-reviewer`).
- Severity-gated review handling via `Approved` / `Approved with concerns` / `Not approved`.
- Git preflight, focused commit discipline, and explicit push confirmation.
- Escalation to the full pipeline when scope or confidence exceeds fastlane limits.

Drop or relax for fastlane:

- formal `docs/plans/` generation by `planner`, unless escalated;
- adversarial plan review/edit refinement;
- dependency wave decomposition and parallel task orchestration;
- per-task fresh-context `verifier` dispatch;
- mandatory baseline/post-wave/final integration-test reconciliation;
- iterative `refine-code` loop by default;
- default worktree creation.

## Design questions to resolve

1. **Route-selection UX:** exactly how should `define-spec` present fastlane vs full plan, and what recommendation heuristic should it use?
2. **Skill shape:** should `fastlane` be spec-only, or also accept todo/freeform input for explicitly trivial tasks?
3. **Checklist persistence:** should the lightweight plan remain ephemeral in the session, be embedded in the coder prompt only, or be saved under a lightweight artifact path for auditability?
4. **Review artifact:** should fastlane persist the one-pass code review under `docs/reviews/`, or is the subagent final message enough for small work?
5. **Model tiers:** default coder/reviewer tiers and whether standalone fastlane review should always use `crossProvider.capable` for independence.
6. **Remediation budget:** one remediation + re-review by default seems right; define the exact stop/escalate behavior.
7. **Push policy:** commit is allowed after review/verification; push should require explicit user confirmation and probably be opt-in per run.
8. **Todo closure:** if a spec came from a todo, should fastlane close it automatically after commit, or ask first?
9. **Docs/README updates:** how should README's typical workflow diagram show the fastlane branch without obscuring the heavyweight path?
