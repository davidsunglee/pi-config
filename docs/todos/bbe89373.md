## Problem

Every subagent in the workflow starts with fresh context and independently discovers codebase structure. The planner does the deepest exploration — following imports, tracing data flow, understanding interfaces — and this is the most expensive read work in the pipeline. Coders in the same wave often re-read overlapping files (shared interfaces, shared types). `define-spec` also needs enough codebase reality to ask good questions. Nobody shares notes.

`rpiv-pi` already has most of the reconnaissance mechanics this workflow needs in its `research` skill:

- `scope-tracer` reads mentioned artifacts, sweeps anchor terms, reads 5–10 key files, and emits a discovery summary plus dense trace-quality questions.
- `research` groups those questions, dispatches analysis agents, synthesizes code references, integration points, architecture insights, precedents/lessons, developer context, and open questions.
- The resulting artifact is a durable, reviewable compression of task-scoped codebase reality.

The opportunity is to **adapt those research mechanics into a scout stage** for this repo's workflow, rather than designing a scout agent from scratch.

## Proposal

Add an optional **scout** stage that runs before `define-spec` and/or `generate-plan`. Given a todo, spec, or freeform task, the scout performs task-scoped codebase reconnaissance and writes a structured **scout brief** that downstream agents consume to avoid repeating broad exploratory reads.

The scout is not a whole-codebase indexer. It is scoped to the task at hand: find the files, interfaces, dependency chains, patterns, tests, precedents, and risk areas relevant to this specific piece of work.

Implementation direction:

- Reuse/adapt the useful parts of `rpiv-pi`'s `research` flow: scope tracing, anchor sweeps, grouped analysis, code references, integration points, precedents, and open questions.
- Do **not** copy the research skill wholesale. A scout brief needs a tighter output contract, deterministic path, non-interactive behavior, and direct integration with `define-spec` / `generate-plan`.
- Prefer a scout-specific agent/prompt over a generic research artifact so downstream consumers can rely on stable sections.

## Where it fits in the pipeline

```text
todo/spec/freeform → [scout] → [define-spec] → generate-plan → execute-plan
```

All bracketed stages are optional, but the preferred flow for ambiguous or non-trivial work is:

```text
todo → scout brief → define-spec Q&A → spec → generate-plan
```

The brief flows into downstream stages:

- **define-spec** consumes the brief to ground its Q&A in actual codebase reality.
- **planner** consumes the brief to skip broad discovery and focus on plan structure, task decomposition, and task-specific verification.
- **plan-reviewer** consumes the brief to check whether the plan incorporated important constraints, risk areas, tests, and patterns from reconnaissance.
- **coders** may receive relevant excerpts later, but this is lower-value because they operate after the plan has concrete file/task scope and must read current files directly.

The scout does **not** re-run between execution waves. By wave 2, wave 1 may have changed the codebase and made the original brief stale. Coders already get file lists in their task prompts and read current files on cheaper models.

## Artifact path and handoff contract

Use this deterministic path:

```text
docs/briefs/TODO-<id>-brief.md
```

For non-todo/freeform inputs, use a dated slug under `docs/briefs/`, but todo-backed briefs should be keyed by todo ID so `define-spec` and `generate-plan` can auto-discover them.

`define-spec` already looks for:

```text
docs/briefs/TODO-<id>-brief.md
```

and preserves this provenance line in generated specs:

```text
Scout brief: docs/briefs/TODO-<id>-brief.md
```

`generate-plan <spec-path>` already extracts a valid `Scout brief:` preamble line and passes the path through to the planner and `refine-plan`. Direct `generate-plan TODO-<id>` should be extended to perform the same deterministic lookup.

## What the scout produces

A structured scout brief, written under `docs/briefs/`.

Recommended format:

```markdown
# Scout Brief: <task title>

Source: TODO-<id>                    <- when todo-backed
Generated at: <ISO timestamp>
Git SHA: <sha>
Model: <provider/model>

## Summary

Short task-scoped overview of the relevant codebase area.

## Relevant Files

Files directly related to the task, each with a one-line role and why it matters.

## Key Interfaces and Types

Contracts, exported types, commands, events, schemas, or APIs the task must understand or modify.

## Dependency / Call Graph

How relevant files relate: imports, calls, implements, registrations, event flow, command flow.

## Patterns and Conventions

Concrete patterns used in the affected area: naming, file organization, error handling, testing style, configuration, dispatch/registration conventions.

## Existing Tests and Test Patterns

Current coverage for the affected code and examples of how similar behavior is tested.

## Risk Areas

Widely depended-on files, brittle seams, stale/generated artifacts, migration hazards, concurrency/state risks, or places where similar changes have broken before.

## Precedents and Lessons

Similar prior changes and follow-up fixes, with commit hashes when git history is available.

## Open Questions / Ambiguities

Questions the scout cannot answer from code alone. These are not asked by scout directly; they are inputs to `define-spec`.

## Confidence Notes

Where the scout is confident vs uncertain, especially if using a cheaper model.
```

This keeps the useful parts of `rpiv-pi` research while making the brief a stable machine-readable artifact for downstream skills.

## Q&A policy and process streamlining

`rpiv-pi`'s `research` skill has a developer checkpoint after analysis and before writing the research artifact. That is appropriate when research itself is the user-facing deliverable, but it is a poor default fit for this pipeline when `define-spec` follows.

Default scout behavior should be **non-interactive**:

- Scout should not ask the developer questions in its own loop.
- Scout should write unanswered questions into `## Open Questions / Ambiguities`.
- `define-spec` should remain the single user-facing Q&A loop for intent, scope, and architecture.
- `define-spec` should use the scout's open questions to ask better, codebase-grounded questions without duplicating a prior scout checkpoint.

Rationale:

1. Avoid two consecutive Q&A loops (`scout` then `define-spec`) asking overlapping questions.
2. Keep scout as cheap reconnaissance, not a deliberation stage.
3. Let `define-spec` ask questions at the right time: after codebase reality is known, but while user intent and requirements are being clarified.
4. Preserve one clear owner for human decisions.

Exception: if the user runs scout as a standalone research deliverable, an optional interactive mode could be added later. That should not be the default pipeline path.

## Direct-to-plan behavior

If the user skips `define-spec` and runs:

```text
scout → generate-plan
```

then blocking ambiguities in the scout brief should not be silently ignored. Preferred behavior:

- If the brief has unresolved, load-bearing open questions, `generate-plan` should recommend running `define-spec` first.
- If the user explicitly continues anyway, planner may proceed but must record the ambiguity in the plan's `## Risk Assessment` and avoid inventing user intent.

This preserves `define-spec` as the normal ambiguity-resolution gate while still allowing experienced users to bypass it.

## Design questions

### 1. When should the scout run?

Options:

- **Always before planning.** Simple, but adds latency and cost for well-scoped tasks where the relevant files are already known.
- **Only when the todo/spec lacks codebase context.** Skip if the input already names specific files/modules and the repo is small enough. Requires a heuristic.
- **User-triggered.** Explicit opt-in. Least friction for simple tasks but requires the user to judge when it is worthwhile.

Recommended initial policy: **user-triggered plus auto-suggested**. Provide a scout skill/command, and have `define-spec` / `generate-plan` suggest it when the input is broad, touches unknown codebase areas, or lacks file/module anchors.

### 2. Is a cheap model good enough?

The scout needs to:

- Follow imports and trace dependency chains — cheap models can often do this reliably.
- Identify patterns and conventions — less certain.
- Characterize design intent and risk areas — judgment-heavy and risky on very cheap models.

Because both `define-spec` and planner may treat the brief as trusted input, default to **standard/Sonnet-tier** unless the brief is constrained to factual extraction only. If using a cheap model, require explicit confidence notes and bias the prompt toward literal evidence: paths, imports, call sites, tests, and quoted patterns rather than design interpretation.

### 3. How does the planner consume the brief?

Options:

- **Injected into the planner prompt.** Simple, but increases prompt size.
- **Referenced as a file.** Keeps prompt lean; planner reads it as needed.
- **Replaces broad exploration.** Prompt says the scout already mapped the relevant area; planner should use the brief for orientation, then verify task-critical files directly.

Recommended: **referenced as a file and load-bearing**. Planner must read the brief when provided, use it for orientation, and still read task-critical files directly before producing tasks.

### 4. What are skip conditions?

Skip or avoid suggesting scout when:

- The repo is tiny and a planner can read the relevant code directly.
- The todo/spec already names exact files, interfaces, tests, and constraints.
- The task is docs-only or configuration-only with obvious scope.
- A brief already exists for the same todo at the current git SHA.
- The input is too vague to scout meaningfully; run `define-spec` first to clarify anchors.

### 5. Brief format and staleness

The brief should not include full file contents by default. It should include structured summaries, paths, line references where useful, and concrete snippets only for non-obvious conventions. Downstream agents should still read current files for task-critical implementation.

The brief must include:

- generated timestamp
- git SHA
- source todo/spec path
- model used
- confidence/uncertainty notes

Downstream consumers should treat a brief generated at a different git SHA as potentially stale and warn before relying on it.

### 6. Is the brief required input or advisory?

If scout exists, make the brief **required when present**:

- `planner` must read and incorporate it.
- `plan-reviewer` must check that important brief findings are reflected in the plan, especially relevant files, risk areas, tests, and conventions.
- If the plan intentionally deviates from the brief, it should record why in `## Risk Assessment`.

If we are not willing to enforce that, then the brief is aspirational and should be dropped from provenance. Recommended: enforce it.

## Integration work

Required changes:

1. Add a scout skill/agent adapted from `rpiv-pi` research mechanics.
2. Write briefs to `docs/briefs/` using deterministic todo-backed paths.
3. Update `define-spec` documentation/prompt to treat `## Open Questions / Ambiguities` from the brief as input to its Q&A loop.
4. Update `generate-plan` direct todo path to auto-detect `docs/briefs/TODO-<id>-brief.md`, not only specs with a `Scout brief:` preamble.
5. Update planner prompt to require reading the scout brief when present and to use it as orientation while still verifying task-critical files.
6. Update plan-reviewer prompt to include brief-coverage checks.
7. Add stale-brief handling based on git SHA.
8. Add skip/suggest heuristics.

## Token cost estimate

Rough comparison for a medium-complexity task in a large codebase:

| Approach | Exploratory reads | Model | Estimated cost |
|----------|------------------|-------|----------------|
| No scout | Planner does all discovery | capable | 150–200K input tokens at capable-tier pricing |
| With scout | Scout does discovery, planner consumes brief | standard + capable | ~100K standard + ~80K capable |
| Cheap factual scout | Scout reports mostly literal references/confidence notes | cheap + capable | ~100K cheap + ~80K capable, but higher risk of missed conventions |

The savings come from shifting broad discovery away from the planner. The planner still reads the brief and the task-critical files directly, but skips much of the exploratory import/grep phase.
