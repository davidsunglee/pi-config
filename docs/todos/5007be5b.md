## Goal

Add deterministic, tested helper scripts/modules for the remaining mechanical orchestration tasks. Helpers may parse structured protocol outputs, fill templates, classify workflow state, and validate protocol/provenance shape. They must not perform substantive implementation verification, independently judge task acceptance criteria, synthesize test artifacts, or bypass verifier/test-runner/code-reviewer subagents.

## Verification boundary

Allowed helper outputs:

- extracted metadata;
- filled prompt text/files;
- structured parse results;
- protocol-shape errors;
- bookkeeping/provenance facts;
- workflow-drift classifications based on explicit allowlists and git metadata.

Forbidden helper outputs:

- implementation acceptance PASS/FAIL derived from local inspection;
- `Criterion N passed because grep found X`-style judgments;
- synthesized `test-runner` artifacts;
- locally-run planner-authored `Verify:` recipe results;
- production-readiness judgments that bypass `refine-code` / reviewer artifacts.

## Remaining helpers to implement

### 1. `parse-test-runner-artifact`

**Scope:** execute-plan-specific, likely `agent/skills/execute-plan/scripts/parse-test-runner-artifact.py`.

**Why useful:** `execute-plan` still needs to mechanically parse the `test-runner` artifact for baseline, post-wave, debugger re-test, and final-gate paths. Centralizing this prevents each session from reimplementing header parsing, exit-code extraction, stable failing-identifier parsing, and non-reconcilable-failure extraction.

**Responsibilities:**

- Given an expected artifact path, parse and validate the `test-runner` artifact.
- Confirm required headers in exact order.
- Extract `EXIT_CODE`.
- Extract `FAILING_IDENTIFIERS` as a byte-for-byte stable identifier set.
- Extract `NON_RECONCILABLE_FAILURES` as a list of evidence entries.
- Report missing/empty/malformed artifact errors mechanically.
- Reuse `_shared/parse-artifact-handoff.py` where marker/path/existence validation is needed, but keep artifact-format validation here.

**Non-goals:**

- Do not run the test command.
- Do not synthesize or write artifacts.
- Do not reconcile failures against `baseline_failures` unless explicitly scoped as a separate integration-gate helper.

**Rough token savings:** **0.5k–2k tokens per execute-plan run when integration tests are enabled**, higher for multi-wave plans with baseline + post-wave + final-gate test cycles.

### 2. `assemble-coder-prompt`

**Scope:** execute-plan-specific, likely `agent/skills/execute-plan/scripts/assemble-coder-prompt.py`.

**Why useful:** Coder prompt filling is repetitive across task dispatches. A helper keeps the task spec verbatim, applies the TDD block consistently, and avoids bespoke template-fill snippets per wave/task.

**Responsibilities:**

- Fill `agent/skills/execute-plan/execute-task-prompt.md` from structured inputs.
- Include the verbatim task spec.
- Include wave, prior-output, and dependency context.
- Include the working directory.
- Include or omit the TDD block based on settings.
- Prefer building on `_shared/fill-template.py` or the same literal placeholder semantics.

**Non-goals:**

- Do not summarize or rewrite the task spec in a way that changes requirements.
- Do not decide whether the coder's output is correct.

**Rough token savings:** **0.5k–1.5k tokens per execute-plan run**. Savings are moderate because the full task prompt still has to be sent to the coder, but it removes repeated prompt-building glue.

---

### 3. `fill-refine-code-prompt`

**Scope:** refine-code-specific wrapper, likely `agent/skills/refine-code/scripts/fill-refine-code-prompt.py` or shared prompt wrapper if a convention is chosen.

**Why useful:** `execute-plan` and standalone review workflows can repeatedly build the same `refine-code` coordinator prompt. A wrapper avoids bespoke snippets for plan goal, plan contents, SHAs, review output paths, iteration budgets, and mode.

**Responsibilities:**

- Fill `agent/skills/refine-code/refine-code-prompt.md` from explicit inputs.
- Include plan goal, plan contents, base/head SHAs, working directory, review output path, max iterations, and mode.
- Preserve exact placeholder replacement semantics.
- Fail closed on missing required inputs or unreplaced placeholders.

**Non-goals:**

- Do not perform review locally.
- Do not inspect the review artifact to decide production readiness beyond mechanical provenance/protocol checks handled elsewhere.

**Rough token savings:** **0.5k–1.2k tokens per run when final review is enabled**. Usually runs once near the end, so savings are smaller than verifier setup but useful for consistency.

### 4. `fill-refine-plan-prompt`

**Scope:** refine-plan-specific / generate-plan workflow helper, likely `agent/skills/refine-plan/scripts/fill-refine-plan-prompt.py` or a shared wrapper around `_shared/fill-template.py`.

**Why useful:** Plan refinement workflows repeatedly fill `agent/skills/refine-plan/refine-plan-prompt.md` with the same categories of inputs. A static helper reduces drift between `generate-plan` and `refine-plan` call sites.

**Responsibilities:**

- Fill `agent/skills/refine-plan/refine-plan-prompt.md` from explicit inputs.
- Include plan path, task artifact/source todo/source spec/scout brief fields, review output path, and model matrix fields required by the prompt.
- Fail closed on missing required fields or unreplaced placeholders.

**Non-goals:**

- Do not perform plan review locally.
- Do not judge plan quality or readiness.

**Rough token savings:** **~0 tokens in execute-plan itself**, but **0.5k–1k tokens per generate/refine-plan workflow**.

---

### 5. `extract-provenance-preamble`

**Scope:** shared helper, likely `agent/skills/_shared/scripts/extract-provenance-preamble.py`.

**Why useful:** `generate-plan` and `refine-plan` both parse provenance from markdown preambles, but the supported line shapes and bounded-read rules can drift. A shared parser keeps provenance extraction deterministic and avoids unsafe parsing of later fenced examples or body text.

**Responsibilities:**

- Read only a bounded preamble region from a markdown file.
- Extract exact supported provenance lines/fields.
- Ignore later document content and fenced examples.
- Return structured provenance fields and protocol-shape errors.

**Non-goals:**

- Do not judge whether the artifact content is good.
- Do not infer missing provenance from body text.

**Rough token savings:** **0.3k–1k tokens per generate/refine-plan workflow**, depending on how many artifact provenance checks are performed. Main value is reducing drift and preventing brittle regex snippets.

---

### 6. `classify-workflow-drift`

**Scope:** mostly generate-plan-specific but should live in shared if it depends on shared workflow-artifact allowlists, likely `agent/skills/_shared/scripts/classify-workflow-drift.py`.

**Why useful:** `generate-plan` has relatively complex mechanical logic for deciding whether repository drift since a scout brief is workflow-only or mixed. Centralizing this avoids repeated git/allowlist snippets and keeps the allowlist semantics aligned with `_shared/workflow-artifact-paths.md`.

**Responsibilities:**

- Use the shared workflow-artifact allowlist.
- Validate scout brief SHA shape and reachability.
- Enumerate `git diff --name-only -z <brief-sha>..HEAD`.
- Classify drift as workflow-only vs mixed.
- Return structured menu/rendering inputs for the caller.

**Non-goals:**

- Do not decide whether a plan should be generated despite substantive drift; the caller/user workflow owns that decision.
- Do not mutate the repo.

**Rough token savings:** **0.5k–1.5k tokens per generate-plan workflow that starts from a scout brief**, especially when drift handling is triggered. Main value is deterministic safety behavior.
