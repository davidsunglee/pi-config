## Problem

`execute-plan` currently keeps the full execution loop in the top-level agent transcript:

- wave dispatch
- coder ↔ verifier retry/remediation loop
- baseline / post-wave / final integration-test gates
- blocked / concerns / retry menus
- bookkeeping between subagent calls

This makes the top-level conversation noisy and mixes user-facing orchestration with a large amount of mechanical inner-loop coordination.

## Goal

Refactor `execute-plan` so the repetitive execution core runs inside a dedicated orchestrating subagent (for example `execute-plan-coordinator`), while the top-level agent keeps the outer user-facing flow.

## Why this seems useful

A dedicated coordinator should:

- keep coder / verifier / test-runner back-and-forth out of the top-level transcript
- localize retry-loop state and reduce context churn
- make the execution state machine easier to reason about
- align with the existing `refine-code` / `code-refiner` pattern
- make resume / restart easier when paired with an on-disk state artifact

## Proposed boundary

### Top-level `execute-plan` keeps

Keep these steps in the top-level agent:

- Step 0: worktree pre-flight
- Step 1: locate plan
- Step 2: validate plan
- Step 3: settings confirmation / customization
- Step 4: existing-output overwrite / skip decision
- final user-facing summary
- linked todo closure
- branch-finishing handoff

The top-level agent should remain the owner of:

- all user-visible setup decisions
- all stop / continue decisions that change global execution mode
- final completion reporting

### New coordinator owns

Move the inner execution loop into a dedicated `execute-plan-coordinator` subagent:

- baseline test capture and reconciliation
- per-wave task dispatch
- coder status parsing
- blocked / concerns handling inside the wave loop
- verifier dispatch and verdict parsing
- retry / remediation loop between coder and verifier
- post-wave integration test gate
- final integration gate
- structured progress / state persistence

## Coordinator model / runtime constraint

The coordinator must run on `pi`, not a non-`pi` CLI, because it must itself dispatch subagents and orchestrations.

This should follow the same style of coordinator dispatch discipline already used by `refine-code` / `code-refiner`.

## Exact handoff contract sketch

Introduce a new handoff contract between the top-level `execute-plan` skill and the coordinator.

### Input contract

The top-level agent dispatches `execute-plan-coordinator` with a single prompt plus durable on-disk inputs.

Preferred inputs:

1. `PLAN_PATH` — absolute path to the plan file
2. `WORKING_DIR` — absolute execution directory
3. `PRE_EXECUTION_SHA` — baseline HEAD before wave execution
4. `SETTINGS_JSON_PATH` — absolute path to a generated JSON settings artifact containing:
   - workspace mode
   - TDD enabled/disabled
   - execution mode
   - wave pacing
   - integration-test enabled/disabled
   - resolved test command or null
   - final-review enabled/disabled
   - final-review max iterations
5. `PLAN_MANIFEST_JSON_PATH` — optional precomputed `extract-plan-tasks.py` result, or else coordinator computes it itself
6. `RUN_STATE_PATH` — absolute path where the coordinator persists structured execution state
7. `RUN_ARTIFACT_DIR` — absolute per-run directory for prompts, reports, verifier artifacts, and test-run logs

Top-level should prefer passing paths rather than inlining large artifacts.

### State artifact contract

The coordinator owns a durable JSON state file at `RUN_STATE_PATH`.

It should persist at least:

- plan path
- working dir
- settings
- current wave / subwave
- task statuses by task number
- retry counts by task number
- baseline failures snapshot
- integration run artifact paths
- verifier report paths
- coder report paths
- latest checkpoint requiring user input, if any
- final outcome, when complete

This state file should be sufficient for:

- resuming after interruption
- debugging a stuck run
- top-level status inspection without replaying transcript context

### Coordinator output contract

The coordinator should always terminate with a compact structured summary in its final message, and the top-level skill should parse that summary mechanically.

Suggested terminal statuses:

- `STATUS: completed`
- `STATUS: needs_user_checkpoint`
- `STATUS: stopped`
- `STATUS: failed`

Required fields / sections:

- `RUN_STATE_PATH: <abs path>`
- `PLAN_PATH: <abs path>`
- `WORKING_DIR: <abs path>`
- `CURRENT_WAVE: <N or done>`
- `COMPLETED_TASKS: <count>`
- `FAILED_TASKS: <count>`
- `REMAINING_TASKS: <count>`

And then status-specific sections.

#### `STATUS: needs_user_checkpoint`

Must include a machine-readable checkpoint block the top-level agent can surface to the user.

Suggested required fields:

- `CHECKPOINT_KIND: blocked_tasks | concerns_review | integration_failures | retry_budget_exhausted | final_gate_failures`
- `CHECKPOINT_ID: <opaque id>`
- `CHECKPOINT_STATE_PATH: <abs path>`
- `OPTIONS: <enumerated options>`
- `USER_MESSAGE_PATH: <abs path to rendered markdown/text prompt>`

The top-level agent should read `USER_MESSAGE_PATH`, present it to the user, collect the decision, then resume or re-dispatch the coordinator with:

- `--resume-state <RUN_STATE_PATH>`
- `--checkpoint-id <CHECKPOINT_ID>`
- `--user-decision <decision payload path or inline token>`

#### `STATUS: completed`

Must include:

- final review status
- review file path if review ran
- final-gate artifact path if integration was enabled
- list of created commits or commit range
- optional todo id detected from the plan source line

#### `STATUS: stopped`

Must include enough information for Step 14-style reporting:

- most recent integration artifact path, if any
- unresolved task numbers
- unresolved failure summary path

#### `STATUS: failed`

Must include:

- a short machine-readable failure label
- human-readable reason
- `RUN_STATE_PATH`
- last successful phase

## Checkpoint protocol sketch

The coordinator should not directly converse with the user for every pause. Instead, it should stop at explicit checkpoints and hand control back to the top-level agent.

That means:

- top-level agent owns the user conversation
- coordinator owns the execution state machine
- coordinator emits a checkpoint summary and exits / suspends cleanly
- top-level agent collects the user answer and re-enters the coordinator

This keeps the user interaction legible while still removing the noisy inner loop from the top-level transcript.

## Recommended implementation shape

A likely implementation path:

1. Add a new coordinator agent definition: `execute-plan-coordinator`
2. Add a prompt / procedure file that defines the coordinator contract
3. Add a parser for the coordinator final summary
4. Add a `run-state` JSON schema / helper module
5. Move Step 7–16 execution logic behind the coordinator boundary first
6. Keep Step 0–4 at top level initially
7. Add resume / checkpoint support once the first coordinator path works

## Important design constraints

- Do not full-context fork the coordinator; pass prompt + artifact paths instead
- Coordinator must not rely on top-level transcript memory for state
- User checkpoints must be structured and resumable
- Top-level skill must remain the authority for setup / customization / final reporting
- The refactor should preserve existing verifier and test-runner boundaries rather than weakening them

## Acceptance criteria

- a new dedicated coordinator subagent exists for the `execute-plan` inner loop
- top-level `execute-plan` no longer owns the coder ↔ verifier ↔ test-runner loop directly
- coordinator persists durable run state on disk
- blocked / concerns / integration-failure pauses are surfaced as structured checkpoints to the top-level agent
- the top-level transcript is materially smaller / cleaner during plan execution
- interrupted runs can be resumed from persisted coordinator state

## Out of scope for the first pass

- redesigning the verifier or test-runner protocols
- changing plan semantics or task extraction semantics
- moving Step 0–4 setup flows into the coordinator
- broad refactors of unrelated `execute-plan` helpers

## Notes

This should probably be modeled as the `execute-plan` equivalent of the existing `refine-code` / `code-refiner` coordinator pattern, but for task-graph execution rather than review/remediation.
