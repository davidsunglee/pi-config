## Goal

Evaluate whether to replace the local custom `agent/extensions/guardrails.ts` extension with the maintained `@aliou/pi-guardrails` package plus customized configuration, while preserving the protections currently relied on in `pi-config`.

## Context

Current local extension: `agent/extensions/guardrails.ts`.

Candidate package: https://github.com/aliou/pi-guardrails (`@aliou/pi-guardrails`).

Initial research notes from commit `bc1fe0b4bcf9353f59d986a6f4a52663cef032cc`:

- It is a Pi package exposing `./src/index.ts` as a Pi extension.
- It supports config layering: global `~/.pi/agent/extensions/guardrails.json`, project `.pi/extensions/guardrails.json`, and memory/session scope, with priority `memory > local > global > defaults`.
- It has policy rules with `noAccess`, `readOnly`, and `none` protections.
- `noAccess` blocks `read`, `write`, `edit`, `bash`, `grep`, `find`, and `ls`; this is broader than the local custom extension's primary `write`/`edit`/`bash` scope.
- It includes structural dangerous-command matching for `rm -rf`, `sudo`, `dd of=`, `mkfs`, `chmod -R 777`, `chown -R`, privileged/container escape patterns, etc.
- It supports optional path-access gating for paths outside cwd, disabled by default.
- Some sensitive built-in rules are disabled by default, including home SSH, home config, and GPG protections.
- Default `.env` protection uses `onlyIfExists: true`, so it may allow creation of new secret files unless overridden.
- Documented limitations: symlinks are lexical only, bash path extraction is best-effort, and noninteractive `ask` degrades to block.

## Current local behaviors to preserve or intentionally drop

The local `guardrails.ts` currently includes protections such as:

- Blocks or confirms dangerous shell commands:
  - recursive deletes (`rm -r`, `rm -rf`, `find -delete`, `find -exec rm`),
  - `sudo`,
  - `mkfs`,
  - `kill -9 -1`,
  - fork bombs,
  - dangerous `chmod 777`,
  - raw device writes, including macOS `/dev/disk*` and `/dev/rdisk*` paths.
- Git guardrails:
  - confirm `git reset --hard`,
  - confirm destructive `git clean -fd` / force-directory clean,
  - confirm `git push --force`,
  - confirm direct push to protected branches such as `main` and `master`,
  - allow dry-run push/clean variants.
- Browser guardrails:
  - block `file://` navigation,
  - confirm browser launch using a real profile (`start.js --profile`).
- Hard-protected paths:
  - `.env`, `.env.*`, `.dev.vars`,
  - `.git`, `.ssh`, `node_modules`, `.venv`, `venv`,
  - Python cache/tool directories,
  - private keys, SSH key-like names, secrets files,
  - `.pypirc`, Cargo credentials, generic credentials paths.
- Soft-protected paths that require confirmation:
  - lockfiles such as `package-lock.json`, `pnpm-lock.yaml`, `poetry.lock`, `Cargo.lock`, `go.sum`, Gradle lock/wrapper files.
- Existing tests in `agent/extensions/guardrails.test.ts` encode many of these expectations.

## Desired outcome

Decide and document one of these paths:

1. Fully replace local `guardrails.ts` with `@aliou/pi-guardrails` plus config.
2. Use `@aliou/pi-guardrails` as the maintained base and keep a small supplemental local extension for behaviors that config cannot express.
3. Keep the custom `guardrails.ts` because the package cannot preserve required behavior without too much complexity.

## Acceptance criteria

- Compare local `guardrails.ts` behavior against `@aliou/pi-guardrails` capabilities using source-backed findings.
- Draft a `guardrails.json` configuration that ports the required local path and command protections where possible.
- Identify behaviors not expressible by package config, especially git guardrails, browser guardrails, raw-device exceptions, and soft lockfile confirmations.
- Decide whether a supplemental `guardrails-extra.ts` is needed.
- Run or adapt relevant existing tests from `agent/extensions/guardrails.test.ts` against the chosen approach.
- Document installation/configuration steps for `@aliou/pi-guardrails` if adopted.
- Ensure the result remains compatible with the planned `pi-gondolin-sandbox` trusted-extension allowlist approach.

## Non-goals

- Implementing the full replacement before a spec/plan unless explicitly requested.
- Treating guardrails as a hard sandbox boundary. It remains defense-in-depth; Gondolin/Safehouse provide stronger containment.
- Removing protections simply because the package defaults do not include them.

## Open questions for define-spec or implementation

- Should this be a separate spec/plan from `pi-gondolin-sandbox`, or folded into the same broader sandbox adoption plan?
- Should `pathAccess` be enabled by default globally, per project, or only for high-risk/Gondolin sessions?
- Should `.env` protections use `onlyIfExists: false` to block creation of new secret files?
- Which git/browser protections must be kept exactly versus merely warning/confirming through generic patterns?
- Should the package be installed globally via `pi install npm:@aliou/pi-guardrails`, pinned through `agent/settings.json`, or included only in selected project settings?
