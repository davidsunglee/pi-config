# Fast Lane Workflow — Implementation Plan

**Source:** TODO-0aac17a1
**Spec:** `docs/specs/2026-05-11-fast-lane-workflow.md`

## Goal

Add `agent/skills/fast-lane/`, a first-class implementation skill that branches from `define-spec`'s Step 8 to a lightweight workflow (checklist → single coder → optional test-runner verification → commit → `refine-code` at reduced budget → todo closure → `finishing-a-development-branch`). The skill is an inline orchestrator that composes existing skills (`commit`, `refine-code`, `finishing-a-development-branch`, `test-driven-development`, `verification-before-completion`) and existing shared helpers (`detect-test-command.py`, `test-runner-dispatch.md`, `parse-test-runner-artifact.py`, `reconcile-test-run.py`, `resolve-model-dispatch.py`, `fill-template.py`, `cleanup-test-runs.py`). It does not create a worktree, does not dispatch a `verifier`, does not push, and does not run a baseline precondition. `define-spec`'s Step 8 is replaced with a 3-option menu plus a heuristic recommendation derived from a new helper.

## Architecture summary

Per the spec's chosen approach, fast lane is an **inline orchestrator skill**. The skill directory `agent/skills/fast-lane/` contains `SKILL.md` (the inline procedure), `README.md` (user-facing docs), `fast-lane-coder-prompt.md` (self-contained coder prompt template), and `scripts/recommend-workflow.py` (heuristic helper used by `define-spec` Step 8 to pick the recommended branch).

Data flow on a successful fast lane run:

1. `define-spec` finishes Step 6 (commit), invokes `recommend-workflow.py` against the just-committed spec, prints the 3-option menu, and on `(f)` invokes `/fast-lane <spec-path>`.
2. The fast lane SKILL.md detects input shape (spec path / `TODO-<id>` / reject freeform), reads the artifact, generates an in-session checklist, and presents the Settings confirmation.
3. After `(s) Start`, the SKILL captures `BASE_SHA`, runs the git preflight, and dispatches a single `coder` subagent with the spec/todo content + confirmed checklist (filled via `fill-template.py` against `fast-lane-coder-prompt.md`).
4. On coder `DONE`/`DONE_WITH_CONCERNS (c)`, the SKILL dispatches `test-runner` against the full project suite (when a test command resolves) and surfaces failures via a `(c)/(b)/(x)` checkpoint. `(b)` opens the on-demand baseline-comparison branch using `reconcile-test-run.py --mode capture` + `--mode reconcile`.
5. On `(c) Continue`, the SKILL invokes the `commit` skill, captures `HEAD_SHA`, invokes `refine-code` with `--max-iterations 3` and `--review-output-path docs/reviews/<spec-name>-fast-lane-review`, closes the linked todo, and invokes `finishing-a-development-branch` (skipped on protected branches).
6. Test-runner artifacts under `docs/test-runs/<spec-name>/` are preserved on any stop exit and cleaned up via `cleanup-test-runs.py` on successful completion. Refine-code review artifacts under `docs/reviews/` follow their own retention policy.

The coder dispatch resolves `(model, cli)` from the run-state `coder_tier` field (default `capable`, mutable via the customize submenu) via `resolve-model-dispatch.py --tier <coder_tier> --agent coder`. Static inspection of `../pi-interactive-subagent` confirms per-task `thinking` is supported by `subagent_run_serial`, forwarded through both pane and headless backends, and overrides agent frontmatter via `params.thinking ?? agentDefs?.thinking` in `pi-extension/subagents/launch-spec.ts`. Therefore the dispatch passes `thinking: "high"` as a per-call `subagent_run_serial` task parameter against `agent: "coder"`. The global `agent/agents/coder.md` default is never modified.

## Tech stack

- **Skill files:** Markdown (SKILL.md, README.md, prompt templates) following the patterns in `agent/skills/execute-plan/`, `agent/skills/define-spec/`, and `agent/skills/scout/`.
- **Helper:** Python 3 (`recommend-workflow.py`) with `argparse`, `json`, `re`, and a single bounded-read of the spec. Tests via stdlib `unittest`.
- **Dispatch primitives:** `subagent_run_serial` (the only dispatch primitive used by fast lane; no parallelism), `commit`, `refine-code`, `finishing-a-development-branch`, and `test-runner` (via the shared `test-runner-dispatch.md` protocol).
- **Test runner:** the project's Python helper test suite via `npm run test:helpers` (extended to include `skills/fast-lane/scripts/tests`).

## Risk Assessment

- **Per-call `thinking: "high"` override was verified by static inspection.** `../pi-interactive-subagent/pi-extension/orchestration/types.ts` exposes task-level `thinking`; `backends/pane.ts` and `backends/headless.ts` forward `params.thinking`; `launch-spec.ts` resolves `effectiveThinking` as `params.thinking ?? agentDefs?.thinking`; and the Pi/Claude launch paths consume `effectiveThinking` as `<model>:<thinking>` or `--effort`. The plan therefore uses `agent: "coder"` with per-call `thinking: "high"` directly. The global `agent/agents/coder.md` default is NOT modified.

- **Heuristic threshold (`requirements_count <= 6`) may be miscalibrated.** Specs in this repo vary in granularity; some 5-bullet specs are deep-workflow material and some 10-bullet specs are fast-lane material. **Mitigation:** the helper exposes `--requirements-threshold N` (default 6) for future tuning, the heuristic's three conditions are ANDed (so a single signal does not flip the recommendation), and the menu is user-overridable — the user can always pick `(d) deep workflow` even when the heuristic recommends `(f)`. Tuning is a separate follow-up if calibration evidence accumulates.

- **`fill-template.py` is generic; missing placeholders in `fast-lane-coder-prompt.md` would only be caught with `--require-all-replaced`.** **Mitigation:** Step 4 of `SKILL.md` explicitly passes `--require-all-replaced`; the helper exits non-zero with a structured `unreplaced placeholders remain` failure, which the orchestrator surfaces verbatim before dispatch. Task 3's acceptance criteria pin the four-placeholder set.

- **`<spec-name>` derivation from the spec filename could collide with execute-plan artifact paths.** Both fast lane (`docs/test-runs/<spec-name>/full-suite.log`) and execute-plan (`docs/test-runs/<plan-name>/baseline.log`) write into `docs/test-runs/`. **Mitigation:** the names diverge in practice because `<spec-name>` derives from `docs/specs/<yyyy-MM-dd>-<topic>.md` (e.g., `2026-05-11-fast-lane-workflow`) and `<plan-name>` derives from `docs/plans/<yyyy-MM-dd>-<topic>.md` — even when the dates and topics match, the filenames are typically distinct because the spec topic and the plan topic differ in long form. If a collision does occur, the cleanup helper's argument validation refuses paths outside the per-subdirectory; both skills clean up their own subdirectory on success.

- **Stash-pop after the `(b)` baseline-comparison branch can produce merge conflicts.** A conflict leaves the working tree in a mixed state. **Mitigation:** Step 7 of `SKILL.md` hard-stops on conflict with verbatim manual-resolution guidance, preserves the stash ref, and preserves the test-runs directory. Fast lane does not attempt automatic conflict resolution.

- **Spec said reconcile-reconcile runs before `git stash pop`; plan does it after.** Spec lines 174–176 order the steps `reconcile capture → reconcile reconcile → git stash pop`, but `git stash push -u` (Step 1 of the sub-flow) sweeps `docs/test-runs/<spec-name>/full-suite.log` into the stash (it is an untracked verification-phase artifact), so the file is not on disk between push and pop. **Why the deviation:** reconcile-reconcile reads `full-suite.log`, which the stash hides until pop restores it. Running reconcile before pop would either crash on a missing file or read a stale path. **How to apply:** Task 4 Step 10 documents the deviation in the SKILL.md prose and reorders the sub-flow to `stash push → baseline test-runner → reconcile capture → stash pop → reconcile reconcile → render three buckets`. `baseline.log` and `baseline-failures.json` are created after stash push and remain on disk through pop, so they are unaffected. Pop conflicts skip the reconcile-reconcile step entirely and hard-stop with preserved artifacts.

- **`define-spec` Step 8's `(x) stop` copy in the spec ("leave spec uncommitted for later") is inconsistent with the actual flow** — Step 8 fires only after Step 6 (commit) has succeeded, so the spec is already committed by the time the menu renders. **Mitigation:** Task 6 of this plan documents `(x)` as "exit silently. The spec remains committed (the menu copy 'leave spec uncommitted for later' is verbatim from the spec but here applies to 'leave the workflow for later' — the commit has already happened in Step 6)." This preserves the spec's verbatim menu text while clarifying behavior in the surrounding prose. (No deviation from spec is recorded; this is a clarification, not an override.)

- **The recommendation helper's stderr-fail path in `define-spec` Step 8 must be benign.** If `recommend-workflow.py` exits non-zero (e.g., the spec path was deleted between commit and the menu render), Step 8 must not crash define-spec. **Mitigation:** Task 6 of this plan documents that Step 8 surfaces the helper's stderr verbatim, falls back to the deep-workflow recommendation, and still renders the menu — the helper is advisory, not load-bearing.
