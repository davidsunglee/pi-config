# Finish remaining static helper scripts for mechanical orchestration — implementation plan

**Source:** `TODO-5007be5b`
**Spec:** `docs/specs/2026-05-07-finish-mechanical-helpers.md`

## Goal

Add nine tested, deterministic Python 3 helper scripts that own the remaining mechanical orchestration work currently embedded in `define-spec`, `generate-plan`, `refine-plan`, `refine-code`, and `execute-plan` markdown procedures: test-runner artifact parsing, coder/refine-code/refine-plan prompt assembly, provenance-preamble extraction, scout-brief workflow-drift classification, refine-plan and refine-code outer-summary parsing, and define-spec mux-backend probing. Adopt every helper at every existing call site that currently hand-rolls the same logic. Each modified existing skill or coordinator-prompt file must shrink (or stay byte-equal where helper invocation already lives) on net. The substantive verification boundary established by the predecessor spec (TODO-c6a7a5d0 / `2026-05-07-execute-plan-mechanical-helpers.md`) is preserved unchanged: helpers may parse protocol output, fill prompts, classify workflow-only drift, validate protocol shape, and emit verbatim user-facing message bodies for outcomes the helper itself classified, but they must not run planner-authored `Verify:` recipes, run integration test commands, write `test-runner` artifacts, judge implementation acceptance criteria, or judge production readiness.

## Architecture summary

- **Three new script directories.** This slice creates `agent/skills/refine-code/scripts/`, `agent/skills/refine-plan/scripts/`, and `agent/skills/define-spec/scripts/` (each with its own `tests/` subdirectory and `tests/fixtures/` subdirectory). It also adds new helpers to the two existing script directories `agent/skills/_shared/scripts/` and `agent/skills/execute-plan/scripts/`. The directory shape (helper `.py` + `tests/` + `tests/fixtures/` + `README.md`) matches the predecessor slice.
- **Nine helpers, one CLI each.** All helpers are Python 3 stdlib-only programs invoked as `python3 <path> [args]`. Each emits structured JSON to stdout on success and structured JSON to stderr on failure with a `failure` field, matching the existing helpers' contract. Exit codes follow the convention: `0` on success, `1` on protocol/parse errors, `2` on usage / unexpected I/O errors. Helpers fail closed on malformed protocol inputs.
- **`parse-test-runner-artifact`** owns parsing of `test-runner` artifacts per `agent/agents/test-runner.md` `## Artifact Format`: validates the eleven required headers in exact order, extracts `EXIT_CODE` as int, returns `FAILING_IDENTIFIERS` as a deduplicated stable-ordered list, returns `NON_RECONCILABLE_FAILURES` as a list of evidence-entry strings (multi-line preserved verbatim, separated by blank lines), and stops at `--- RAW RUN OUTPUT BELOW ---` (does NOT return raw output). It does NOT reconcile against `baseline_failures` — set arithmetic stays in `execute-plan/SKILL.md`.
- **`assemble-coder-prompt`** fills `agent/skills/execute-plan/execute-task-prompt.md` from structured inputs (`{TASK_SPEC}`, `{CONTEXT}`, `{WORKING_DIR}`, `{TDD_BLOCK}`) using the same single-pass literal-substitution semantics as `_shared/fill-template.py`. The TDD block is included verbatim from `agent/skills/execute-plan/tdd-block.md` when enabled, omitted otherwise. Substitution is duplicated in-script (no shell-out to `fill-template.py`), mirroring `assemble-verifier-prompt.py`.
- **`fill-refine-code-prompt`** fills `agent/skills/refine-code/refine-code-prompt.md` from explicit inputs (`{PLAN_GOAL}`, `{PLAN_CONTENTS}`, `{BASE_SHA}`, `{HEAD_SHA}`, `{REVIEW_OUTPUT_PATH}`, `{MAX_ITERATIONS}`, `{MODEL_MATRIX}`, `{WORKING_DIR}`). Same single-pass literal-substitution semantics. Fails closed on missing required inputs or any unreplaced `{IDENTIFIER}` token in the output.
- **`fill-refine-plan-prompt`** fills `agent/skills/refine-plan/refine-plan-prompt.md` from explicit inputs (`{PLAN_PATH}`, `{TASK_ARTIFACT}`, `{SOURCE_TODO}`, `{SOURCE_SPEC}`, `{SCOUT_BRIEF}`, `{ORIGINAL_SPEC_INLINE}`, `{STRUCTURAL_ONLY_NOTE}`, `{MAX_ITERATIONS}`, `{STARTING_ERA}`, `{REVIEW_OUTPUT_PATH}`, `{WORKING_DIR}`, `{MODEL_MATRIX}`). Same semantics as `fill-refine-code-prompt`.
- **`extract-provenance-preamble`** reads only a bounded preamble region from a markdown file and extracts exactly three supported line shapes: `Source: TODO-<8-char-hex>`, `Scout brief: docs/briefs/<filename>`, and `Git SHA: <40-char-lowercase-hex>`. Two bound modes selectable via `--mode`: `spec` (read until first `## ` heading or first 40 lines, whichever comes first) and `brief` (read first 8 lines). Lines that don't match an exact supported shape are silently ignored. Matching lines that appear after the preamble bound are ignored. Returns structured fields plus protocol-shape errors when applicable (e.g., a `Git SHA:` value that is not 40 lowercase hex characters).
- **`classify-workflow-drift`** owns the full git pipeline for `generate-plan/SKILL.md` Step 1b's brief-staleness classifier: reads the brief preamble for `Git SHA:` (delegating via subprocess to `extract-provenance-preamble.py --mode brief`), runs `git rev-parse HEAD`, runs `git merge-base --is-ancestor <brief-sha> HEAD`, and on success runs `git diff --name-only -z <brief-sha>..HEAD`. Classifies enumerated paths against the allowlist defined in `agent/skills/_shared/workflow-artifact-paths.md` using the documented prefix-as-directory-boundary semantics. Returns a JSON blob with one of six `outcome` tags (`silent_continue`, `workflow_only`, `mixed_changes`, `uninspectable_a`, `uninspectable_b`, `uninspectable_c`), structured fields (`brief_sha`, `head_sha`, `non_workflow_paths`, `error`), and the verbatim `message_body` for non-silent outcomes (informational message for `workflow_only`; menu body byte-equal to one of the four variants currently inlined in Step 1b for `mixed_changes`, `uninspectable_a`, `uninspectable_b`, and `uninspectable_c`). The skill prints the returned message and routes on the `outcome` tag; the interactive `(c)`/`(x)` response handling stays in the skill.
- **`parse-refine-plan-summary`** parses the compact `refine-plan/SKILL.md` Step 11 outer summary (the public summary consumed by `generate-plan/SKILL.md` Step 5): `STATUS:`, `COMMIT:`, `PLAN_PATH:`, the `REVIEW_PATHS:` block (one `- <path>` per line), `STRUCTURAL_ONLY:`, and the optional `FAILURE_REASON:` line. Validates required-field presence per status (e.g., `FAILURE_REASON:` only with `STATUS: failed`).
- **`parse-refine-code-summary`** parses the compact `refine-code-prompt.md` Output Format (the coordinator's output): `STATUS:`, the `## Summary` block (`Iterations:`, `Issues found:`, `Issues fixed:`, `Issues remaining:`), the optional `## Remaining Issues` block, the `## Review File` block, and the optional `## Failure Reason` block. Validates required-field presence per status.
- **`detect-mux-backend`** owns `define-spec/SKILL.md` Step 1's mechanical work in full: Step 1a env-var + `command -v` probe (rules 1–8 byte-equal with the runtime's `pi-extension/subagents/cmux.ts` + `backends/select.ts` precedence, including rule 3's no-fallback-on-pinned-`PI_SUBAGENT_MUX` behavior), Step 1b user-input override scan (when `--user-input <text>` is supplied; matches the documented substring set), and Step 1c verbatim status-message construction. Returns a JSON blob: `branch` (`mux`|`inline`), `backend` (one of `cmux`/`tmux`/`zellij`/`wezterm` when mux, else `null`), `reason` (short tag identifying which rule fired), and `status_message` (the verbatim status line for the chosen branch). Probe-only — does not spawn any mux backend; emits no text to stdout/stderr beyond the documented JSON contract.
- **Helper home for `detect-mux-backend`.** Per the spec's Open Question, this slice places `detect-mux-backend` at `agent/skills/define-spec/scripts/detect-mux-backend.py`. Rationale: define-spec is the single consumer in this slice, and the predecessor convention placed single-consumer helpers under the consumer skill's `scripts/` directory (e.g. execute-plan-specific helpers under `agent/skills/execute-plan/scripts/`). The helper's README documents the placement; future consumers (e.g. a hypothetical `define-brief`) would migrate the helper to `_shared/scripts/` if/when that becomes a multi-consumer concern, per the spec's Open Question footer.
- **Adoption sites slim, never grow.** Every modified existing skill or coordinator-prompt file MUST have both line count and byte count strictly ≤ its current counts after edits. The detailed mechanical contract moves into the helper's `--help` text, tests, and helper-directory README. Skills retain at most one-line "Invoke `<script>` for `<purpose>`; surface its structured error/canonical message on failure" pointers.
- **No tool-surface changes.** Every helper invocation site already has `bash` available (the predecessor spec narrowly added `bash` to `plan-refiner`; every other adopter — `define-spec`, `generate-plan`, `refine-plan`'s SKILL, `refine-code`'s SKILL, `execute-plan`, and `code-refiner` — already had `bash`). No agent definition is modified in this slice.
- **Helper test runner.** `agent/package.json`'s `test:helpers` script is extended to chain `python3 -m unittest discover` against the three new test directories (`refine-code/scripts/tests`, `refine-plan/scripts/tests`, `define-spec/scripts/tests`) after the two existing ones. The plan's `## Test Command` is `cd agent && npm run check`, which exercises both extension tests and the full helper test run.

## Tech stack

- Python 3 stdlib only (`argparse`, `json`, `re`, `pathlib`, `subprocess`, `sys`, `os`, `shutil`, `tempfile`, `unittest`). No third-party deps.
- Existing infrastructure: `agent/skills/_shared/workflow-artifact-paths.md` (read by `classify-workflow-drift` for the allowlist text); the markdown templates `agent/skills/execute-plan/execute-task-prompt.md`, `agent/skills/execute-plan/tdd-block.md`, `agent/skills/refine-code/refine-code-prompt.md`, `agent/skills/refine-plan/refine-plan-prompt.md` (read by the prompt-fill helpers); the git CLI (called by `classify-workflow-drift`).
- Shell glue: each adopted call site invokes the helper via `python3 <repo>/<script>.py [args]`, captures stdout/JSON, and surfaces stderr on failure. No new bash sub-runtime; calls go through the same `bash` tool already available to all SKILL.md-driven orchestrators.
- Internal helper paths: every helper that reads a default template or delegates to another repository helper MUST resolve that path from `Path(__file__)` (or an equivalent script-relative path), not from the process cwd. CLI examples may use repo-root paths, but implementations must pass when tests run from `cd agent && npm run test:helpers` and when skills invoke helpers from the repository root.
- Test harness: `unittest` (stdlib). Tests run via `python3 -m unittest discover -s <dir> -p "test_*.py"` from `agent/`.

## File Structure

### New files

#### Shared helpers

- `agent/skills/_shared/scripts/extract-provenance-preamble.py` (Create) — Python 3 CLI. Accepts `--file <path>`, `--mode <spec|brief>`. Reads only the bounded preamble region: in `spec` mode, reads up to (and excluding) the first `## ` heading or the first 40 lines, whichever comes first; in `brief` mode, reads the first 8 lines. Within the bounded region, scans line-by-line for these exact line shapes (anchored, no leading whitespace, no trailing whitespace except a single newline):
  - `Source: TODO-<8-char-hex>` — the hex chars are `[0-9a-f]{8}` exactly.
  - `Scout brief: docs/briefs/<filename>` — `<filename>` is `[^/]+` (no slash; basename of a file under `docs/briefs/`).
  - `Git SHA: <sha>` — `<sha>` MUST match `[0-9a-f]{40}`. If a `Git SHA:` line is present in-bound but the value does not match, the helper fails closed with a `git_sha_malformed` protocol error in stderr JSON `.failure`. Lines that don't match any of the three shapes are silently ignored (per the spec's "Lines that don't match an exact supported shape are silently ignored" rule). Matching lines that appear after the bound (e.g. inside fenced code blocks below the first `## ` heading in spec mode) are out of bounds and ignored. On success emits `{"source_todo": "<id or null>", "scout_brief": "<filename or null>", "git_sha": "<sha or null>", "mode": "<spec|brief>"}` to stdout. On a `git_sha_malformed` protocol error, emits `{"failure": "git_sha_malformed", "value": "<observed>", "mode": "<spec|brief>"}` to stderr and exits 1. `--help` describes the three line shapes and two modes byte-equal.
- `agent/skills/_shared/scripts/classify-workflow-drift.py` (Create) — Python 3 CLI. Accepts `--brief-path <path>` (required) and `--working-dir <path>` (default cwd). Owns the full git pipeline:
  1. Run `agent/skills/_shared/scripts/extract-provenance-preamble.py --file <brief-path> --mode brief` to obtain `git_sha` (the brief's SHA). If the helper exits non-zero with `git_sha_malformed`, OR the brief's preamble is missing the `Git SHA:` line, route to outcome `uninspectable_a`.
  2. Run `git rev-parse HEAD` from `--working-dir`. On non-zero exit, route to `uninspectable_c` with `<head-sha>` rendered as `<unknown>` and `<error>` set to the failing command's stderr.
  3. If `brief_sha == head_sha`, route to `silent_continue` (no message).
  4. Run `git merge-base --is-ancestor <brief-sha> HEAD`. On non-zero exit, route to `uninspectable_b`.
  5. Run `git diff --name-only -z <brief-sha>..HEAD`. On non-zero exit, route to `uninspectable_c` with the failing stderr in `<error>`. On success, parse the NUL-separated output (split bytes on `\0`, drop the trailing empty string) into a path list.
  6. Read `agent/skills/_shared/workflow-artifact-paths.md` and parse the four allowlist prefixes (`docs/briefs/`, `docs/specs/`, `docs/todos/`, `docs/plans/`) from the `## Allowlist` section. Match each enumerated path against each allowlist prefix using the prefix-as-directory-boundary rule (a path matches a prefix iff it starts with that prefix and the prefix ends with `/`).
  7. If every enumerated path matches a prefix → `workflow_only`. If at least one enumerated path matches NO prefix → `mixed_changes`, with `non_workflow_paths` set to the ordered list of unmatched paths (preserve git diff order; do not re-sort).

  On all outcomes, emits a JSON blob to stdout: `{"outcome": "<tag>", "brief_path": "<path>", "brief_sha": "<sha or null>", "head_sha": "<sha or null or '<unknown>'>", "non_workflow_paths": [...], "error": "<verbatim git stderr or null>", "message_body": "<verbatim user-facing message body or null>"}`. The `message_body` is null for `silent_continue` and is the byte-equal text from `generate-plan/SKILL.md` Step 1b's current four menu variants (or the `workflow_only` informational message) for the other five outcomes. Always exits 0 (drift-classification outcomes are not script failures). Exits non-zero only on argument-parse errors (exit 2) or unexpected I/O errors (exit 2). `--help` enumerates the six outcome tags and the message-body templates byte-equal.

#### Execute-plan helpers

- `agent/skills/execute-plan/scripts/parse-test-runner-artifact.py` (Create) — Python 3 CLI. Accepts `--artifact <path>` and optional `--final-message <path>` + `--expected-path <path>` (when both are supplied, the helper internally invokes the shared `parse-artifact-handoff.py` via a script-relative path with `--marker TEST_RESULT_ARTIFACT --final-message <path> --expected-path <path> --check-existence --check-non-empty` first; on its non-zero exit, surface the handoff helper's stderr verbatim and exit non-zero). Reads the artifact file. Validates that the eleven required headers (`PHASE`, `COMMAND`, `WORKING_DIRECTORY`, `EXIT_CODE`, `TIMESTAMP`, `FAILING_IDENTIFIERS_COUNT`, `FAILING_IDENTIFIERS:`, `END_FAILING_IDENTIFIERS`, `NON_RECONCILABLE_COUNT`, `NON_RECONCILABLE_FAILURES:`, `END_NON_RECONCILABLE_FAILURES`) appear at the start of their lines in this exact order. Stops parsing at the first occurrence of `--- RAW RUN OUTPUT BELOW ---`; does NOT return the raw output. Parses:
  - `PHASE`, `COMMAND`, `WORKING_DIRECTORY`, `TIMESTAMP` → strings (the substring after `<HEADER>: `).
  - `EXIT_CODE` → int (the substring after `EXIT_CODE: ` parsed via `int()`; on parse failure, fail closed with `exit_code_malformed`).
  - `FAILING_IDENTIFIERS_COUNT`, `NON_RECONCILABLE_COUNT` → int with the same rule.
  - `FAILING_IDENTIFIERS:` block → the lines between `FAILING_IDENTIFIERS:` and `END_FAILING_IDENTIFIERS` (each line trimmed of trailing newline only). Validate that the raw identifier-line count equals `FAILING_IDENTIFIERS_COUNT`; otherwise fail closed with `failing_identifiers_count_mismatch`. After the count check passes, deduplicate while preserving first-occurrence order for the returned JSON.
  - `NON_RECONCILABLE_FAILURES:` block → the contents between `NON_RECONCILABLE_FAILURES:` and `END_NON_RECONCILABLE_FAILURES`, split by single blank lines into entries (per the artifact format's "Each non-reconcilable evidence entry MUST be separated from the next by a single blank line" rule). Each entry is preserved verbatim including internal newlines (multi-line stack traces are common). The result count MUST equal `NON_RECONCILABLE_COUNT`; otherwise fail closed with `non_reconcilable_count_mismatch`.

  On success emits `{"phase": "...", "command": "...", "working_directory": "...", "exit_code": <int>, "timestamp": "...", "failing_identifiers_count": <int>, "failing_identifiers": [...], "non_reconcilable_count": <int>, "non_reconcilable_failures": [...]}` to stdout. Header-order or count-mismatch failures emit `{"failure": "<label>", "artifact": "<path>", "detail": "<short detail>"}` to stderr and exit 1. The complete enumeration of failure labels: `header_missing` (a required header is absent), `header_out_of_order` (a required header appears after a later one), `failing_identifiers_count_mismatch`, `non_reconcilable_count_mismatch`, `exit_code_malformed`, `count_field_malformed` (a count header's value isn't an int), `artifact_missing_or_empty` (the file is missing or zero-byte), `raw_output_marker_missing` (the `--- RAW RUN OUTPUT BELOW ---` line is absent before EOF — the structured header MUST be terminated by that marker per the artifact format). `--help` lists the JSON shape and every failure label byte-equal.
- `agent/skills/execute-plan/scripts/assemble-coder-prompt.py` (Create) — Python 3 CLI. Accepts `--template <path>` (default `agent/skills/execute-plan/execute-task-prompt.md`), `--task-spec <path|->`, `--context <path|->`, `--working-dir <path>`, `--tdd-block <enabled|disabled>` (default `enabled`), `--tdd-block-template <path>` (default `agent/skills/execute-plan/tdd-block.md`), `--output <path|->`. Reads the template. Reads each text input. When `--tdd-block enabled`, reads the TDD block template's full body verbatim. When `--tdd-block disabled`, the TDD block value is the empty string (per `execute-plan/SKILL.md` Step 8's "if TDD is enabled... substitute its full contents verbatim. If TDD is disabled, substitute the empty string"). Builds the placeholder map `{TASK_SPEC, CONTEXT, WORKING_DIR, TDD_BLOCK}` — the four placeholders in `execute-task-prompt.md`. Substitutes via the same single-pass literal-substring algorithm `fill-template.py` documents (no recursive expansion of values containing `{OTHER}`); the algorithm is duplicated in-script (no runtime shell-out to `fill-template.py`), mirroring `assemble-verifier-prompt.py`. After substitution, scans the output for any remaining `\{[A-Z_][A-Z0-9_]*\}` token; on any remaining, fails closed with `{"failure": "unreplaced placeholders remain", "unreplaced": [...]}` to stderr and exits 1. Writes to `--output`. On missing required input file, emits `{"failure": "input missing or unreadable", "input": "<which>"}` to stderr and exits 2. `--help` documents every input shape and the four placeholders.

## Risk Assessment

- **Adoption-task size-delta failure.** Each adoption task asserts that the modified file's line count and byte count do not exceed their pre-edit baselines. If a `coder` worker rewrites prose without removing enough redundant content first, the size constraint may fail. Mitigation: each adoption task's first checkbox step is "Capture pre-edit line and byte counts"; subsequent steps are explicit about what to remove (e.g., "the eight bullet placeholder list", "the four menu variants enumerated inline"); verification recipes use `wc -l -c <file>` against the documented baselines. Each baseline number was sampled at planning time from the current file.
- **`classify-workflow-drift` message-body byte-equal regression.** The helper hardcodes the four menu variants from `generate-plan/SKILL.md` Step 1b, but the SKILL is being concurrently slimmed in Task 12 to remove those exact variants. If Task 6 and Task 12 implement the bodies with subtle whitespace / newline differences, downstream callers comparing the helper output to the original prose would fail. Mitigation: Task 6's tests assert byte-equal match against verbatim string constants (the test fixtures hardcode the expected message bodies). Task 12 removes the inline prose AFTER Task 6 has landed and its tests pass — Wave-2 → Wave-3 → Wave-4 ordering enforces this.
- **`detect-mux-backend` PATH-stub portability.** Task 9's tests use `make_stub_dir()` to inject empty executable files for `cmux`/`tmux`/`zellij`/`wezterm` and prepend the directory to `PATH`. This relies on `shutil.which` finding the stub files. On Windows or unusual shells the executable mode `0o755` may not be honored; this codebase targets darwin/linux per the runtime, so this is acceptable. Tests use `os.pathsep` so PATH is constructed correctly across platforms.
- **`parse-test-runner-artifact` count-mismatch interaction with deduplication.** The artifact format documents `FAILING_IDENTIFIERS_COUNT` as the size of the deduplicated stable-identifier set per `agent/agents/test-runner.md` ("The resulting collection is a deduplicated set."). The helper's strict count-validation rule (raw line count must equal COUNT) would fail if the artifact's writer ALSO dedupes. Mitigation: Task 1's implementation validates COUNT against the raw line count BEFORE deduplication. The fixture `test-runner-artifact-stable-failures.txt` contains COUNT and identifier lines that match exactly. The dedupe-but-mismatch case is exercised in `test_duplicate_identifier_dedupes`'s clarified rule: COUNT must equal the raw line count; if the writer dedupes both COUNT and identifiers, the validation passes; if the writer emits dupes in the block but a deduplicated COUNT, validation fails closed. This mirrors the test-runner agent's documented contract (it dedupes both).
- **`fill-refine-plan-prompt` placeholder count drift.** The helper expects exactly twelve placeholders. If `refine-plan-prompt.md` is later edited to add a thirteenth placeholder (e.g. a new metadata field) without updating the helper, `--require-all-replaced` will catch the drift on first invocation — fail closed with `unreplaced placeholders remain`. Same mitigation applies to `fill-refine-code-prompt` and `assemble-coder-prompt`.
- **`extract-provenance-preamble` 40-line / 8-line bound is heuristic.** The bounds are inherited from the existing `head -n 40` and `head -n 8` prose. If a future spec or brief grows a longer preamble, the bound may cut off a load-bearing line. Mitigation: the bounds are tunable via the helper's source (single point of change); the spec explicitly locks in exactly two modes for this slice; new modes are deferred to a follow-up todo per the spec's Open Questions footer.
- **Same-directory write conflicts in Wave 1.** Tasks 1+2 both add files to `agent/skills/execute-plan/scripts/`; Tasks 5+7 don't conflict (5 is shared, 7 is refine-plan); Tasks 1+2 add distinct `.py` and `test_*.py` files but both could try to update the same `README.md`. Mitigation: Wave 1 tasks do NOT touch READMEs — README updates are deferred to Task 10 (Wave 3), which owns all README writes as a single batch.
- **Predecessor README reuse.** The two existing READMEs at `agent/skills/_shared/scripts/README.md` and `agent/skills/execute-plan/scripts/README.md` already exist with the predecessor's helper bullets. Task 10 INSERTS new bullets without removing existing ones. The acceptance recipe (`grep -c "...|..."` returns at least 2) protects against accidental removal of the predecessor bullets but does not enforce ordering; a coder who appends bullets to the wrong position is acceptable as long as the bullets are present.
- **Verification-boundary slip in `classify-workflow-drift`.** The spec authorizes the helper to emit verbatim user-facing menu bodies for outcomes the helper itself classified — a narrow exception to the verification-boundary rule. The risk is that a future helper iteration could be tempted to also handle the `(c)`/`(x)` interactive routing. Mitigation: Task 6's acceptance criteria include `Verify: open agent/skills/_shared/scripts/classify-workflow-drift.py and confirm the body contains no input(, no sys.stdin.readline(), and no prompt-loop pattern.` The helper writes the menu to JSON and exits.
- **Helper-test-runner sequential execution.** `agent/package.json`'s `test:helpers` chains the five `python3 -m unittest discover` invocations with `&&`. A failure in any one short-circuits the rest, which means a developer running `npm run check` may not see all helper failures at once. This is the existing predecessor behavior and is acceptable — `npm run test:helpers` is a fast pre-commit signal, not an exhaustive-failures dashboard.
